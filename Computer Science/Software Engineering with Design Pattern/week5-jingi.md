## [COMMON-161] 객체지향 프로그래밍이 무엇이고, 주요 특징을 설명해 주세요.

답변:

객체지향 프로그래밍은 프로그램을 객체 단위가 서로 상호작용하는 방식으로 설계하는 것을 의미합니다. 이떄 객체는 데이터와 그 데이터를 목적에 맞게 다루는 함수로 구성 됩니다. 따라서 기능을 단순히 순차적인 과정으로 보는 것보다 각 객체가 어떤 책임을 맡고 서로 어떻게 메시지를 주고받는지에 초점을 둡니다.

주요 특징으로는 캡슐화, 상속, 다형성, 추상화가 있습니다. 

캡슐화는 객체의 상태와 그 상태를 변경하는 방법을 하나로 묶고, 외부에서는 제공되는 기능만 사용할 수 있도록 복잡한 내부 구현을 숨기는 것을 의미합니다. 이를 통해 내부 구현을 바꾸더라도 외부 코드의 영향을 줄일 수 있습니다.

상속은 기존 클래스의 속성과 기능을 확장해 새로운 클래스를 만드는 것이고, 다형성은 동일한 인터페이스로 여러 구현을 다룰 수 있는 것을 의미합니다.

추상화는 여러 대상에서 핵심적인 공통점을 뽑아 무엇을 하는지 정의하는 것을 의미합니다.

## [COMMON-163] SOLID 원칙에 대해 설명해 주세요.

답변:

SOLID는 객체지향 설계를 유지보수하기 쉽게 만드는 다섯 가지 원칙입니다. 다섯 가지 원칙은 단일 책임 원칙, 개방-폐쇄 원칙, 리스코프 치환 원칙, 인터페이스 분리 원칙, 의존성 역전 원칙이 있습니다.

단일 책임 원칙은 클래스가 하나의 책임만을 가져야 한다는 원칙이고, 개방-폐쇄 원칙은 확장에는 열려 있고 변경에는 닫혀 있어야 한다는 원칙입니다. 리스코프 치환 원칙은 자식 클래스가 부모 클래스를 대체할 수 있어야 하고, 대체되어도 기능을 깨뜨리지 않아야 한다는 원칙입니다. 인터페이스 분리 원칙은 사용하지 않는 메서드에 의존하지 않도록 인터페이스를 분리해야 한다는 원칙이고, 의존성 역전 원칙은 상위 모듈이 하위 모듈에 직접 의존하지 않고 둘 다 추상화에 의존해야 한다는 원칙을 의미합니다.

## [COMMON-164] 단일 책임 원칙이 무엇이고, 왜 중요한지 설명해 주세요.

답변:

단일 책임 원칙은 클래스가 하나의 책임만을 가져야 한다는 원칙을 의미합니다.

예를 들어 주문 서비스가 사용자 인증, 주문 금액 계산, 데이터 저장, 알림 전송까지 모두 담당하게 될 경우, 하나의 클래스가 여러 개의 책임을 갖기 때문에 특정 기능에 변경이 발생할 경우, 다른 기능에 영향을 줄 수 있습니다. 이런 경우 인증, 계산, 저장, 알림 책임을 분리하면 각 부분을 독립적으로 변경할 수 있기 때문에 유지보수 측면에서 단일 책임 원칙이 중요하다고 볼 수 있습니다.

## [COMMON-165] 의존성 역전 원칙이 무엇이고, 어떤 장점이 있는지 설명해 주세요.

답변:

의존성 역전 원칙은 상위 모듈이 하위 모듈에 직접 의존하지 않고 둘 다 추상화에 의존해야 한다는 원칙을 의미합니다.

의존성 역전 원칙이 지켜지지 않는다면, 하위 모듈이 수정될 때 상위 모듈도 수정해야 하는 상황이 발생할 수 있습니다. 따라서 의존성 역전 원칙을 준수하면 추상화에 의존함으로써 각 모듈이 서로의 수정에 영향을 주지 않는 유연한 수정이 가능합니다.

## [COMMON-166] 인터페이스를 사용하는 이유와 장단점을 설명해 주세요.

답변:

인터페이스는 여러 구현체가 공통적으로 제공해야 할 기능을 정의할 때 사용합니다. 사용하는 쪽은 구체적인 클래스가 아니라 인터페이스에 의존할 수 있기 때문에, 구현체를 교체하거나 여러 구현체를 다형성으로 사용할 수 있습니다.

이를 통해 역할과 구현을 분리함으로써 각 구현체 간의 결합도가 감소한다는 장점이 있습니다. 반면, 인터페이스가 너무 많으면 구조가 복잡해지고, 오히려 이해하기 어려워질 수 있다는 단점이 있습니다.

## [COMMON-167] 추상 클래스와 인터페이스의 차이에 대해 설명해 주세요.

답변:

추상 클래스는 공통 상태나 기본 구현을 포함하여 하위 클래스가 구현해야 하는 메서드도 정의할 수 있는 클래스입니다. 따라서 클래스들 사이에 공통 데이터를 공유해야하고, 기본 구현을 재사용하고 싶을 때 적합합니다.

인터페이스는 추상 클래스와 달리, 하위 클래스가 구현해야 하는 메서드만을 정책으로 정의할 수 있는 클래스입니다. 구현체가 여러 인터페이스를 구현할 수 있고, 서로 다른 계층의 클래스도 같은 역할로 묶을 수 있다는 점이 차이입니다.

## [COMMON-170] Factory Method Pattern이 무엇이고, 어떤 상황에서 사용할 수 있는지 설명해 주세요.

답변:

팩토리 메서드 패턴은 객체를 생성하는 메서드를 상위 클래스에서 정의해 두고, 실제로 어떤 구체적인 객체를 생성할지는 하위 클래스가 결정하도록 하는 생성 패턴입니다. 객체를 사용하는 전체 흐름과 객체를 생성하는 책임을 분리할 수 있다는 점이 핵심입니다.

예를 들어 하나의 목적을 가진 객체가 여러 구현체로 나뉘고, 상황에 따라 생성해야 하는 구현체가 달라지는 경우에 사용할 수 있습니다. 이때 상위 클래스는 객체를 생성한 뒤 사용하는 공통 작업 흐름을 정의하고, 하위 클래스는 팩토리 메서드를 구현해 자신에게 맞는 구체적인 객체를 생성합니다. 이렇게 하면 사용하는 쪽은 각 구현체의 생성자나 내부 생성 과정을 알 필요가 없고, 새로운 구현체가 추가되더라도 기존 상위 클래스의 코드를 수정하지 않고 하위 생성 클래스를 추가할 수 있습니다.

따라서 객체 종류가 늘어날 가능성이 있거나 생성 과정이 복잡하고, 생성하는 객체에 따라 공통 작업 흐름은 유지되어야 하는 상황에 사용할 수 있습니다. 반대로 생성할 객체가 적고 생성 로직도 단순하다면 클래스와 호출 단계만 늘어날 수 있다는 단점이 있습니다.

## [COMMON-172] Observer Pattern이 무엇이고, 어떤 상황에서 사용할 수 있는지 설명해 주세요.

답변:

옵저버 패턴은 한 객체의 상태가 변경되었을 때, 그 객체에 의존하는 여러 객체에 변경 사실을 알리는 패턴입니다. 상태를 관리하는 객체가 주체이고, 알림을 받는 객체가 옵저버를 의미합니다.

예를 들어 하나의 데이터가 처리되었을 때, 다른 객체가 이를 알고 코드가 실행되어야 하는 상황에 사용할 수 있습니다.

## [COMMON-173] MVC 패턴이 무엇이고, 각 구성 요소의 역할을 설명해 주세요.

답변:

MVC는 애플리케이션 코드를 Model, View, Controller로 나누어 설계하는 구조를 의미합니다. Model은 데이터와 핵심 비즈니스 로직을 담당하고, View는 사용자에게 데이터를 보여주는 화면을 담당합니다. Controller는 사용자의 요청이나 입력을 받아 필요한 Model의 동작을 호출하고, 그 결과를 View에 전달하는 역할을 합니다.

## [COMMON-174] Layered Architecture가 무엇이고, 어떤 장단점이 있는지 설명해 주세요.

답변:

Layered Architecture는 애플리케이션의 동작을 역할별 계층으로 나누고, 각 계층이 통신하게 하는 구조를 의미합니다. 일반적으로 프레젠테이션 계층, 서비스 계층, 도메인 계층, 데이터 접근 계층으로 나눌 수 있습니다. 예를 들어 컨트롤러는 요청을 받고 서비스에 흐름을 위임하며, 서비스가 저장소를 통해 데이터를 다루는 방식입니다.

장점은 역할과 의존 관계가 명확해져서 코드를 이해하기 쉽고, 한 계층의 변경이 다른 계층으로 영향을 주는 것을 방지할 수 있다는 점입니다.

하지만 작은 기능도 여러 계층을 거쳐야 해서 코드가 늘어날 수 있다는 단점이 있습니다.

## [COMMON-175] 관심사의 분리가 무엇이고, 좋은 코드 구조에 왜 중요한지 설명해 주세요.

답변:

관심사의 분리는 하나의 모듈이나 클래스가 여러개의 작업을 수행하지 않고, 각 관심사를 독립적인 구성 요소로 나누는 원칙을 의미합니다.

관심사를 분리하면 특정 관심사를 별도로 분리하여 독립적으로 테스트하거나 재사용할 수 있어 좋은 코드 구조가 될 수 있습니다.

## [COMMON-176] 결합도와 응집도가 무엇이고, 좋은 설계에서는 각각 어떻게 관리되어야 하는지 설명해 주세요.

답변:

결합도는 한 모듈이 다른 모듈에 얼마나 강하게 의존하는지를 의미하고, 응집도는 하나의 모듈 안에 관련된 책임과 데이터가 얼마나 잘 모여 있는지를 의미합니다. 일반적으로 결합도는 낮추고 응집도를 높이는 것이 좋은 설계라고 볼 수 있습니다.

## [COMMON-177] 테스트 코드가 필요한 이유와 단위 테스트, 통합 테스트의 차이를 설명해 주세요.

답변:

테스트 코드는 코드가 의도한 대로 동작하는지 자동으로 확인하고, 해당 코드가 다른 기능에 영향을 주지는 않은지 빠르게 발견하기 위해 필요합니다. 또 테스트 코드는 코드의 기대 동작을 보여주는 문서 역할도 하고, 리팩토링할 때 방향성을 제공할 수 있습니다.

단위 테스트는 보통 하나의 클래스나 함수처럼 작은 단위를 외부와 분리해서 검증하는 테스트 범위를 의미합니다. 실행이 빠르고 실패 원인을 찾기 쉽지만, 다른 클래스나 함수와 연결하여 테스트를 하는 것에는 제한적입니다. 통합 테스트는 단위 테스트와는 다르게 여러 모듈을 통합하여 상호작용하는 것을 검증하는 방식입니다.

## [COMMON-178] 리팩토링이 무엇이고, 리팩토링 시 주의해야 할 점을 설명해 주세요.

답변:

리팩토링은 코드의 실행 결과가 변경되지 않는 선에서 내부 코드를 개선하는 작업입니다. 중복 로직을 메서드로 추출하거나, 클래스를 분리하는 작업을 예로 들 수 있습니다.

리팩토링이 실제 코드의 실행 결과 변경으로 이어지지 않도록 주의해야 합니다. 리팩토링 중에 기능까지 바꾸면 문제가 생겼을 때 원인을 구분하기 어렵기 때문입니다.

## [COMMON-179] 기술 선택 시 trade-off를 설명한다는 것은 어떤 의미인지 설명해 주세요.

답변:

기술 선택에서 trade-off를 설명한다는 것은 그 기술을 선택함으로서 얻는 이점과 발생할 수 있는 단점을 설명하는 것을 의미합니다. 예를 들어 캐시를 사용하면 응답 속도와 데이터베이스 부하를 줄일 수 있지만, 캐시 데이터에 대한 정합성과 운영 복잡성을 관리해야 합니다.

따라서 기술 선택 시 trade-off는 주어진 프로젝트나 서비스의 환경에 가장 적합한 기술을 선택할 수 있도록 확실한 근거를 찾아나가는 과정을 의미한다고 생각합니다.

## [COMMON-180] 본인의 프로젝트에서 기술적 의사결정을 설명할 때 어떤 구조로 답변하면 좋을지 설명해 주세요.

답변:

먼저 어떤 선택을 했는지에 대한 기술적 의사결정을 밝히고, 이에 따른 트레이드 오프를 설명하면서 이 프로젝트에 부합하는 이유가 무엇인지를 답변해 나갈 것 같습니다.

타당한 기술적 의사결정을 위해서는 해당 기술의 트레이드오프를 명확하게 이해하고, 장점이 프로젝트 환경에서 어떻게 효과적으로 작용하는지, 반대로 단점은 프로젝트 환경에서 어떻게 극복할 수 있는지를 찾아보는 것이 필요하다고 생각합니다.

결론적으로 기술적 의사결정은 정답인 기술을 맞히는 것보다, 프로젝트의 요구사항과 제약 조건에 맞춰 합리적인 근거로 선택했다는 점을 전달하는 것이 중요하다고 생각합니다. 따라서 기술의 객관적인 트레이드오프를 설명하고, 제가 선택한 이유와 실제 결과, 그리고 한계까지 구체적으로 연결해서 말하는 것이 좋은 답변이라고 생각합니다.
