## [COMMON-162] 캡슐화, 상속, 다형성, 추상화에 대해 설명해 주세요.

답변:

캡슐화는 데이터와 기능을 하나로 묶어서 다른 곳에서 사용할때 내부 구현을 함부로 건드리지 못하게 하는걸 마치 캡슐처럼 만든다고 하는 것이다 
상속은 부모와 자식 관계처럼 부모가 가진 특징을 자식이 물려받아 새로운 기능을 하는 객체를 만드는 것이다 
다형성은 자바로 봤을때 오버라이딩과 같은 기능으로 같은 인터페이스를 사용하지만 그 내부 기능은 다르게 구현해놔서 객체에 따라 다르게 동작을 할 수 있는 걸 의미한다 
추상화는 부모의 기능을 복잡하게 구현해두는게 아니라 최대한 상위로 갈수록 인터페이스처럼 설계도만 만들어두어서 이후 상속할때 구체화하는 식으로 구현하려는 객체지향프로그래밍의 특성이다. 

정리하면 
추상화 → 필요한 것만 정의하고
캡슐화 → 내부 구현과 데이터를 숨기고
상속 → 기존 코드를 재사용·확장하고
다형성 → 같은 방식으로 호출해도 객체에 따라 다르게 동작하게 한다.

## [COMMON-164] 단일 책임 원칙이 무엇이고, 왜 중요한지 설명해 주세요.

답변:
Single Responsibility Principle - 단일 책임 원칙 
하나의 클래스는 하나의 책임만 가져야 한다
예를 들어 하나의 클래스에서 다양한 기능을 제공하려고한다면 하나의 기능만 수정해야할때도 계속 그 클래스를 수정해야함 
단일 책임 원칙은 한마디로 하면 클래스의 변경 이유가 하나여야한다고 이해하면 된다 = 하나의 클래스가 하나의 책임만 가지도록 한다 
변경이 발생했을 때 해당 책임과 관련된 코드만 수정할 수 있도록 하는 원칙 

중요한 이유: 책임별로 클래스를 분리해서 변경의 영향을 최소화시키기 위함

## [COMMON-165] 의존성 역전 원칙이 무엇이고, 어떤 장점이 있는지 설명해 주세요.

답변:
Dependency Inversion Principle - 의존성 역전 원칙 
"고수준 모듈(정책/비즈니스 로직)은 저수준 모듈(구체적인 구현 세부사항)에 직접 의존해서는 안 되고, 둘 다 추상화(인터페이스)에 의존해야 한다 "
이에 대한 예시 : 
❌ 주문 서비스 → 카카오페이 : 이 경우 주문 서비스가 카카오페이라는 특정 기술을 직접 알고있음 
🅾️ 주문 서비스 → Payment 인터페이스 ← 카카오페이
                              ← 토스페이
                              ← 네이버페이

-> 구체적인 구현에 직접 의존하지 않고 인터페이스 같은 추상화를 통해 의존하도록 만드는 원칙으로,
이렇게 구현한다면 구현이 변경되더라도 이를 사용하는 쪽의 코드를 수정할 필요가 적어져서 변경에 유연하고 유지보수하기 쉬워짐

## [COMMON-169] Singleton Pattern이 무엇이고, 장단점은 무엇인지 설명해 주세요.

답변:
Singleton Pattern은 특정 클래스의 객체가 프로그램 전체에서 하나만 생성되도록 보장하는 패턴
보통 생성자를 private으로 막고, 
정적 메서드(getInstance())를 통해서만 인스턴스를 얻도록 구현한다 

장점:

리소스를 많이 쓰는 객체(DB 커넥션 풀, 설정 관리자, 로거 등)를 한 번만 생성해 메모리/성능 효율
전역 상태를 일관되게 관리 가능

단점:

전역 상태이기 때문에 어디서든 값을 바꿀 수 있어 예측 불가능한 부작용 발생 가능
테스트 시 상태가 테스트 간 공유되어 격리(isolation)가 깨짐 → 테스트 순서에 따라 결과가 달라지는 원인이 될 수 있음
숨겨진 의존성이 됨 (생성자 주입이 아니라 내부에서 직접 호출하므로 의존관계가 코드에 드러나지 않음)
멀티스레드 환경에서 인스턴스 생성 시 동기화 처리 필요

## [COMMON-170] Factory Method Pattern이 무엇이고, 어떤 상황에서 사용할 수 있는지 설명해 주세요.

답변:

Factory Method 패턴은 객체 생성 로직을 별도의 메서드(팩토리 메서드)로 캡슐화해서, 
클라이언트 코드가 구체적인 클래스를 직접 new하지 않고 상위 인터페이스/추상 클래스를 통해 객체를 얻도록 하는 생성 패턴이다. 

사용 상황:

생성할 객체의 타입이 런타임에 조건에 따라 결정될 때 (예: 파일 확장자에 따라 다른 Parser 객체 생성)
객체 생성 로직이 복잡하거나, 향후 새로운 타입이 추가될 가능성이 높을 때
클라이언트 코드가 구체 클래스에 결합되지 않도록 하고 싶을 때 (OCP 실현)

## [COMMON-171] Strategy Pattern이 무엇이고, 어떤 문제를 해결할 수 있는지 설명해 주세요.

답변:

Strategy 패턴은 알고리즘(행위)을 별도의 클래스로 캡슐화하고, 런타임에 서로 교체 가능하게 만드는 행위 패턴이다. 
클라이언트는 어떤 전략(구현체)을 쓰는지와 무관하게 동일한 인터페이스로 호출한다 . 

해결하는 문제:

if-else나 switch문으로 알고리즘 분기를 처리하면, 새로운 케이스가 추가될 때마다 기존 코드를 계속 수정해야 함(OCP 위반). Strategy 패턴은 새로운 전략 클래스를 추가만 하면 되므로 기존 코드 수정 없이 확장 가능
동일한 문제를 여러 알고리즘으로 풀 수 있을 때, 알고리즘 선택 로직과 알고리즘 자체를 분리

## [COMMON-172] Observer Pattern이 무엇이고, 어떤 상황에서 사용할 수 있는지 설명해 주세요.

답변:

Observer 패턴은 한 객체(Subject)의 상태가 변경되면, 그 객체를 구독(등록)하고 있는 다른 객체들(Observer)에게 자동으로 알림이 가서 반응하도록 하는 행위 패턴이다. 
Publish-Subscribe 구조의 기반이 되는 패턴이다. 

사용 상황:

하나의 이벤트에 대해 여러 객체가 각자 다른 방식으로 반응해야 할 때 (예: 주문 완료 시 이메일 발송 + 재고 차감 + 로그 기록을 동시에 트리거)
발행자(Subject)가 구독자(Observer)의 구체적인 타입을 몰라도 되게 하고 싶을 때 → 결합도 감소
UI 이벤트 처리(버튼 클릭 → 여러 리스너 실행), 실시간 데이터 갱신(주식 가격 변동 알림) 등

## [COMMON-173] MVC 패턴이 무엇이고, 각 구성 요소의 역할을 설명해 주세요.

답변:
MVC는 애플리케이션을 Model, View, Controller 세 가지 역할로 분리하는 아키텍처 패턴이다.

Model: 데이터와 비즈니스 로직을 담당. 데이터의 상태와 그 상태를 변경하는 규칙을 가지고 있으며, View나 Controller에 대해 알지 못함
View: 사용자에게 보여지는 화면(UI)을 담당. Model의 데이터를 표현만 하고 직접 데이터를 변경하지 않음
Controller: 사용자 입력을 받아 Model을 조작하고, 그 결과에 따라 적절한 View를 선택/갱신. View와 Model 사이의 중재자 역할

흐름: 사용자 입력 → Controller가 받아서 처리 → Model 상태 변경 → View가 변경된 Model을 반영해 갱신

장점: 관심사 분리로 각 요소를 독립적으로 개발/테스트 가능, 동일한 Model에 대해 여러 View 구현 가능 
단점: 규모가 커지면 Controller가 비대해지기 쉽고(Fat Controller), View와 Model 사이 계층이 늘어나면 데이터 흐름 추적이 복잡해질 수 있음

## [COMMON-174] Layered Architecture가 무엇이고, 어떤 장단점이 있는지 설명해 주세요.

답변:

계층형 아키텍처는 시스템을 역할에 따라 수평적인 계층(Layer)으로 나누고, 각 계층은 바로 아래(또는 인접한) 계층에만 의존하도록 제한하는 아키텍처 스타일이다. 
일반적으로 Presentation(화면) → Application/Business(비즈니스 로직) → Persistence(데이터 접근) → Database 순으로 구성된다.

장점:

관심사가 명확히 분리되어 각 계층을 독립적으로 개발/테스트/교체 가능 (예: DB를 MySQL에서 PostgreSQL로 바꿔도 상위 계층 영향 최소화)
팀원별로 계층을 나눠 병렬 개발 가능
구조가 직관적이라 학습 곡선이 낮음

단점:

계층을 거쳐야 하는 요청이 많아지면 불필요한 오버헤드 발생 (단순 조회에도 모든 계층을 통과해야 함)
계층 간 강한 순차 의존이 생기면 하나의 변경이 여러 계층에 파급될 수 있음
잘못 설계하면 계층 경계가 흐려져(예: Presentation에서 직접 DB 접근) 이점이 사라짐

## [COMMON-175] 관심사의 분리가 무엇이고, 좋은 코드 구조에 왜 중요한지 설명해 주세요.

답변:
관심사의 분리는 프로그램을 서로 다른 관심사별로 나누어, 각 부분이 하나의 관심사에만 집중하도록 설계하는 원칙이다. 
SRP가 클래스 레벨의 원칙이라면, 관심사 분리는 더 넓은 범위에 적용되는 상위 개념이다.

중요한 이유:

변경의 파급 효과 최소화: 한 관심사의 로직이 바뀌어도 다른 관심사에 영향을 주지 않음
이해 용이성: 코드를 읽을 때 한 번에 하나의 개념만 신경 쓰면 됨 (인지 부하 감소)
독립적 테스트 가능: 관심사별로 나뉘어 있으면 각각을 격리해서 테스트하기 쉬움
재사용성: 특정 관심사를 다른 컨텍스트에서도 재사용 가능

## [COMMON-177] 테스트 코드가 필요한 이유와 단위 테스트, 통합 테스트의 차이를 설명해 주세요.

답변:
테스트 코드가 필요한 이유 
회귀 방지: 코드를 수정했을 때 기존 기능이 깨지지 않았는지 자동으로 빠르게 검증
리팩토링 안전망: 테스트가 있으면 구조를 과감히 개선해도 동작 보장을 확신할 수 있음
문서 역할: 테스트 코드 자체가 "이 함수는 이런 입력에 이렇게 동작해야 한다"는 명세 역할
설계 품질 개선: 테스트하기 쉬운 코드를 짜려다 보면 자연스럽게 SRP, DIP 등을 지키게 됨
빠른 피드백: 사람이 매번 수동으로 검증하는 것보다 훨씬 빠르게 결함을 발견

단위 테스트 : 함수, 메서드, 클래스 같은 가장 작은 단위를 외부 의존성과 격리(Mock 처리)해서 검증. 빠르고, 실패 시 원인 파악이 명확함.
통합 테스트 : 여러 모듈/컴포넌트가 실제로 연결되어 함께 동작할 때의 상호작용을 검증. DB, API, 외부 서비스 연동 등 단위 테스트에서는 잡히지 않는 '경계면' 문제를 발견.

## [COMMON-178] 리팩토링이 무엇이고, 리팩토링 시 주의해야 할 점을 설명해 주세요.

답변:
리팩토링은 소프트웨어의 외부 동작은 그대로 유지하면서 내부 구조만 개선하는 작업이다. 

주의해야 할 점:

테스트 코드가 선행되어야 함: 리팩토링 전후 동작이 동일한지 검증할 안전망(테스트)이 없으면, 리팩토링이 아니라 '동작이 바뀔 수도 있는 수정'이 됩니다.
작은 단위로 점진적으로 진행: 한 번에 큰 구조를 바꾸면 문제 발생 시 원인 파악이 어려움. 작은 커밋 단위로 나눠서 각 단계마다 테스트 통과를 확인
기능 추가와 분리: 리팩토링과 새 기능 개발을 같은 커밋/PR에 섞으면 코드 리뷰와 문제 추적이 어려워짐
성능 영향 확인: 구조 개선이 때로는 성능 저하를 유발할 수 있어 필요시 벤치마크 확인

## [COMMON-180] 본인의 프로젝트에서 기술적 의사결정을 설명할 때 어떤 구조로 답변하면 좋을지 설명해 주세요.

답변:

기술적 의사결정을 설명할 때는 문제 상황 → 대안 비교 → 선택 이유(기준) → 결과(정량적 지표) → 회고/한계의 구조로 답변하는 것이 효과적입니다.

문제 상황: 무엇이 문제였는지, 어떤 제약 조건이 있었는지 구체적으로 제시
대안 비교: 고려했던 다른 선택지들과 각각의 장단점
선택 이유: 어떤 기준(성능, 비용, 팀 상황, 마감기한 등)으로 최종 선택을 했는지
결과: 가능하면 정량적 지표로 결과를 제시 (Before/After 비교)
회고: 이 선택의 한계나 아쉬운 점, 다시 한다면 무엇을 다르게 할지
