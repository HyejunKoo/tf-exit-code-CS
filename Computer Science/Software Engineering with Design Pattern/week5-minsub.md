## [COMMON-162] 캡슐화, 상속, 다형성, 추상화에 대해 설명해 주세요.

답변: 

- 캡슐화: 객체의 상태와 동작을 하나로 묶고 접근 제어자로 외부 접근을 제한하는 정보 은닉을 제공합니다.
- 상속: 부모 클래스의 속성과 기능을 자식 클래스가 물려 받아 코드를 재사용하고 확장을 용이하게 합니다.
- 다형성: 하나의 타입으로 여러 객체를 다룰 수 있고, 동일한 메서드를 호출해도 객체 실제 타입에 따라 다르게 동작하는 특성입니다.
- 추상화: 객체의 공통적인 특징을 모델링하는 과정입니다. 세부적인 구현은 숨기고, 인터페이스나 추상 클래스를 통해 역할만 정의합니다.

## [COMMON-163] SOLID 원칙에 대해 설명해 주세요.

답변: 객체지향 설계에서 유지보수성과 확장성을 높이기 위한 다섯 가지 설계 원칙입니다.

- SRP(단일 책임 원칙)는 하나의 클래스는 하나의 책임만 가져야 한다는 원칙,
- OCP(개방-폐쇄 원칙)는 확장은 열려 있고, 변경은 닫혀 있어야 한다는 원칙,
- LSP(리스코프 치환 원칙)는 자식 클래스에서 부모 클래스를 대체할 수 있어야 한다는 원칙,
- ISP(인터페이스 분리 원칙)는 클라이언트가 사용하지 않는 메서드에 의존하지 않도록 인터페이스를 분리해야 한다는 원칙,
- DIP(의존성 역전 원칙)는 구체 구현이 아닌 추상화에 의존해야 한다는 원칙입니다.

## [COMMON-164] 단일 책임 원칙이 무엇이고, 왜 중요한지 설명해 주세요.

답변: 단일 책임 원칙은 하나의 클래스나 모듈이 하나의 책임만 가져야 한다는 원칙입니다.

예를 들어서 주문 서비스가 주문 생성, 결제 처리, 알림 발송, 로그 기록까지 모두 담당하면 책임이 많아집니다.
결제 정책이 바껴도 수정해야 하고, 알림 방식이 바껴도 수정돼야 하는데, 이러면 유지보수나 변경이 어려워질 수 있습니다.

그래서 SRP를 잘 지켜서 코드 응집도를 높이고, 변경에 강한 구조를 만드는 것으로 알고 있습니다.

## [COMMON-165] 의존성 역전 원칙이 무엇이고, 어떤 장점이 있는지 설명해 주세요.

답변: 구체 클래스가 아닌, 인터페이스나 추상 타입에 의존한다는 의미입니다.

예를 들어 주문 서비스가 `KakaoPayClient`에 직접 의존하면 결제 수단이 바뀔 때 주문 서비스 코드도 수정될 수 있는데,
`PaymentClient` 인터페이스에 의존하고 실제 구현체를 `KakaoPayClient`, `CardPaymentClient`로 분리하면 결제 방식이 바껴도 영향을 받지 않습니다.

그래서 계층 간 결합도를 낮추고, 구현체 교체를 쉽게 할 수 있습니다.

## [COMMON-167] 추상 클래스와 인터페이스의 차이에 대해 설명해 주세요.

답변: 

- 추상 클래스는 상태와 동작을 묶어주는 부모 역할
```java

abstract  class Animal {
    String name;
    
    public Animal(String name) {
        this.name = name;
    }
    
    public void sleep() {
        System.out.println(name + "가 잠을 자요.");
    }
    
    // 자식이 직접 구현해야 되는 추상 메서드
    abstract void makeSound();
}

class Dog extends Animal {
    public Dog(String name) {
        super(name);
    }
    
    @Override
    void makeSound() {
        System.out.println("멍멍");
    }
}
```

- 인터페이스는 기능을 정의해두고 활용해서 쓰는 용도이다.
```java
interface Flyable {
    void fly();
}

interface Swimmable {
    void swim();
}

class Duck implements Flyable, Swimmable {
    @Override
    public void fly() {
        System.out.println("오리 날다!");
    }
    
    @Override
    public void swim() {
        System.out.println("오리 수영한다!");
    }
}

class Airplane implements Flyable {
    @Override
    public void fly() {
        System.out.println("비행기가 난다!");
    }
}
```

## [COMMON-171] Strategy Pattern이 무엇이고, 어떤 문제를 해결할 수 있는지 설명해 주세요.

답변: 전략 패턴은 실행 중 교체 가능한 알고리즘이나 정책을 전략 객체로 분리하는 패턴입니다.

예를 들어서 할인 정책이 정률, 정액, 쿠폰으로 나뉜다고 할 때 하나의 메서드 안에서 `if-else`로 다 처리하면 정책이 늘어날 때마다 코드 복잡성이 올라갑니다.
이럴 때 할인 정책을 `DiscountStrategy` 인터페이스로 추상화하고, 각 정책을 별도 구현체로 분리할 수 있습니다.

그래서 새로운 전략이 추가될 때 기존 코드 수정을 별로 하지 않고, 구현체를 추가하는 방식으로 확장할 수 있고, 알고리즘 교체를 유연하게 만듭니다.

## [COMMON-172] Observer Pattern이 무엇이고, 어떤 상황에서 사용할 수 있는지 설명해 주세요.

답변: 옵저버 패턴은 객체의 상태 변화가 발생했을 때, 그 객체에 의존하는 여러 객체들에게 알림을 전달하는 패턴입니다.

예를 들어 주문이 완료되었을 때 재고 차감, 사알림 발송, 포인트 적립 같은 후속 작업이 필요할 수 있는데, 주문 서비스가 이 모든 후속 작업을 직접 호출하면 결합도가 높아집니다.
그래서 옵저버 패턴을 사용해서 주문 완료 이벤트를 발행하고, 관심 있는 객체들이 이런 이벤트를 구독해서 처리할 수 있도록 만듭니다.

그래서 이벤트 알림, UI 이벤트 처리, 발행-구독 구조 등에서 사용하는 것으로 알고 있습니다.

## [COMMON-173] MVC 패턴이 무엇이고, 각 구성 요소의 역할을 설명해 주세요.

## [COMMON-174] Layered Architecture가 무엇이고, 어떤 장단점이 있는지 설명해 주세요.

답변: 애플리케이션을 역할에 따라 계층적으로 나누는 아키텍처입니다.
표현 계층, 애플리케이션 계층, 데이터 계층 등으로 나누는데, 예를 들어 Spring에서 Controller, Service, Repository 구조가 이 계층형 구조와 부합합니다.

계층 별로 역할이 분리돼서 구조 이해가 쉽고, 유지보수나 테스트가 쉽습니다.
다만, 단순한 기능에도 계층을 모두 나눠서 진행하면 코드가 장황해질 수 있습니다.


[보완]

이 레이어 아키텍처는 기본적으로 코드 안에서 역할을 어떻게 나눌 것인지에 대한 논리적 분리이다.
코드 유지보수성 및 재사용성을 높이기 위함.

대표적인 3 Layer 

- 표현 계층: UI, 컨트롤러
- 비즈니스 로직 계층: 서비스 (핵심 비즈니스 로직)
- 데이터 액세스 계층: 리포지토리(DAO - DB랑 통신하는 계층)

직접적인 메서드 호출을 통해 데이터를 주고 받음(네트워크 통신 불필요)

반면, 3-Tier 아키텍처는 인프라(서버)를 어떻게 구성할 것인가에 초점을 맞춘 물리적 분리이다.
보안, 확장성, 서버 부하 분산에 초점을 맞춤.

- 각 티어가 물리적으로 분리된 장비나 독립된 네트워크에 존재

대표적인 3 Tier

- 표현 티어: 웹 서버, 클라이언트
- 애플리케이션 티어: WAS, API 서버
- 데이터 티어: 데이터베이스 서버

반드시 네트워크 통신(HTTP, TCP/IP)을 통해서만 데이터를 주고 받음.

## [COMMON-175] 관심사의 분리가 무엇이고, 좋은 코드 구조에 왜 중요한지 설명해 주세요.

답변: 서로 다른 책임을 가진 코드를 분리하는 설계 원칙입니다.

컨트롤러에 요청/응답, 서비스에 비즈니스 로직, 리포지토리에 데이터 접근을 담당하도록 분리해서 유연한 구조를 갖추곤 합니다.

그래서 관심사 분리는 유지보수, 가독성이나 확장성을 높이는데 중요합니다.

## [COMMON-176] 결합도와 응집도가 무엇이고, 좋은 설계에서는 각각 어떻게 관리되어야 하는지 설명해 주세요.

답변: 결합도는 코드의 어떤 부분을 수정하면 다른 부분이 영향을 받을 가능성이 커지는, 서로 얼마나 의존하는지를 의미합니다.

응집도는 한 클래스 안의 기능이 얼마나 잘 모여있는지를 의미합니다.

그래서 결합도를 낮추고, 응집도를 높여서 모듈이나 클래스가 명확한 책임을 갖되, 다른 클래스랑은 필요한 인터페이스로 느슨하게 연결되도록 설계하는 것이 좋습니다.

- OrderProcessor가 주문 흐름 제어, DB SQL 쿼리 작성, 메일 서버 설정을 한 곳에서 처리하고 있는데, 예를 들어 메일 서버 주소만 바껴도 이 클래스를 수정해야 함 -> 낮은 응집도

```java
interface InventoryRepository {void decreaseStock(String itemId);}
interface PaymentService {boolean pay(int amount);}
interface NotificationService {void notify(String target, String message);}

public class OrderProcessor {
    
    // 인터페이스만 의존하게 설계
    private final InventoryRepository inventory;
    private final PaymentService payment;
    private final NotificationService notification;
    
    // 주입 받기
    public OrderProcessor(InventoryRepository inventory, PaymentService payment, NotificationService notification) {
        this.inventory = inventory;
        this.payment = payment;
        this.notification = notification;
    }
    
    // 주문의 전체 흐름만 제어 (높은 응집도)
    public void processOrder(Order order) {
        inventory.decreaseStock(order.getItemId());
        
        boolean isPaid = payment.pay(order.getAmount());
        
        if (isPaid) {
            notification.notify(order.getUserEmail(), "주문이 완료되었습니다.");
        }
    }
}
```

- 재고 줄이고 -> 결제하고 -> 알림 보내는 주문의 흐름에만 집중 (높은 응집도)
- 결제 방식 다른 걸 추가해도 코드 수정 불필요 (낮은 결합도)

## [COMMON-183] Interface Segregation Principle을 예시와 함께 설명해 주세요.

답변: 인터페이스 분리 원칙은 클라이언트가 사용하지 않는 메서드에 의존하지 않도록 인터페이스를 작게 분리해야 한다는 원칙입니다.

## [COMMON-184] Dependency Injection이 무엇이고, 어떤 장점이 있는지 설명해 주세요.

답변: 의존성 주입은 객체가 필요한 의존성을 직접 생성하지 않고 외부에서 주입받는 방식입니다.

ex) 컨트롤러가 서비스를 직접 `new`로 만들지 않고, 생성자를 통해 서비스를 주입받는 것이 DI.
스프링에서 컨트롤러, 서비스, 리포지토리 등을 빈으로 등록해서 스프링 컨테이너가 필요한 의존성을 자동으로 주입함.

객체 간 결합도를 낮출 수 있고, 구현체 교체도 쉬워지고, 또 스프링은 DI를 통해서 빈을 컨테이너가 관리하니까 `@Transactional` 같은 AOP 기반 부가 기능 적용도 적합해진다.
