## [COMMON-161] 객체지향 프로그래밍이 무엇이고, 주요 특징을 설명해 주세요.

답변:

- 객체지향 프로그래밍 (Object-Oriented Programming, OOP)
  - 프로그램을 데이터(속성)와 그 데이터를 조작하는 행위(메서드)를 하나의 단위인 객체(Object)로 묶어 설계하는 패러다임
  - 절차지향이 "함수 중심"이라면, OOP는 "객체 중심"으로 문제 영역을 모델링
- 주요 특징
  - 캡슐화: 내부 구현을 숨기고 필요한 인터페이스만 노출
  - 상속: 기존 클래스의 속성·행위를 확장·재사용
  - 다형성: 동일한 인터페이스로 다양한 구현체를 처리
  - 추상화: 핵심 개념만 추출하여 복잡성을 줄임
- OOP를 사용하는 이유
  - 현실 세계의 개념(사용자, 주문, 결제 등)을 코드로 자연스럽게 표현
  - 모듈화·재사용성 향상 → 대규모 시스템 유지보수에 유리
  - 변경 영향 범위를 객체 단위로 격리 가능

## [COMMON-162] 캡슐화, 상속, 다형성, 추상화에 대해 설명해 주세요.

답변:

- 캡슐화 (Encapsulation)
  - 객체의 내부 상태(필드)를 외부에서 직접 접근하지 못하게 숨기고, public 메서드를 통해서만 조작
  - private/protected 접근 제어, getter/setter 등으로 데이터 무결성 보호
  - 내부 구현 변경 시 외부 코드에 영향을 최소화
- 상속 (Inheritance)
  - 기존 클래스(부모)의 속성과 메서드를 자식 클래스가 물려받아 확장
  - 공통 로직 중복 제거, IS-A 관계 표현 (예: Dog IS-A Animal)
  - 단, 과도한 상속은 결합도를 높이므로 컴포지션을 우선 고려
- 다형성 (Polymorphism)
  - 같은 타입(인터페이스·부모 클래스) 참조로 서로 다른 구현 객체를 처리
  - 오버로딩(컴파일 타임): 같은 이름, 다른 매개변수
  - 오버라이딩(런타임): 자식이 부모 메서드를 재정의, 실제 객체 타입에 따라 호출
- 추상화 (Abstraction)
  - 복잡한 내부를 숨기고 핵심 기능·개념만 노출
  - 추상 클래스, 인터페이스로 "무엇을 할 수 있는지"만 정의하고 "어떻게"는 구현체에 위임

## [COMMON-163] SOLID 원칙에 대해 설명해 주세요.

답변:

- SOLID
  - 객체지향 설계에서 유지보수성·확장성을 높이기 위한 5가지 원칙의 약자
- S — Single Responsibility Principle (단일 책임 원칙)
  - 클래스는 하나의 변경 이유만 가져야 함 → 하나의 책임만 담당
- O — Open-Closed Principle (개방-폐쇄 원칙)
  - 확장에는 열려 있고, 수정에는 닫혀 있어야 함 → 새 기능은 추가하되 기존 코드 변경 최소화
- L — Liskov Substitution Principle (리스코프 치환 원칙)
  - 자식 클래스는 부모 클래스를 대체해도 프로그램 동작이 깨지지 않아야 함
- I — Interface Segregation Principle (인터페이스 분리 원칙)
  - 클라이언트는 사용하지 않는 메서드에 의존하지 않도록 인터페이스를 작게 분리
- D — Dependency Inversion Principle (의존성 역전 원칙)
  - 고수준 모듈이 저수준 모듈에 의존하지 않고, 둘 다 추상화(인터페이스)에 의존

## [COMMON-164] 단일 책임 원칙이 무엇이고, 왜 중요한지 설명해 주세요.

답변:

- 단일 책임 원칙 (Single Responsibility Principle, SRP)
  - 하나의 클래스(또는 모듈)는 단 하나의 책임, 즉 하나의 변경 이유만 가져야 한다는 원칙
  - "책임" = 변경의 원인이 되는 관심사 (예: 사용자 인증, 이메일 발송, DB 저장)
- 위반 예시
  - UserService가 회원 가입, 이메일 발송, 로그 기록까지 모두 처리 → 변경 이유가 3가지
- 준수 예시
  - UserService(가입 로직), EmailService(발송), AuditLogger(로그)로 분리
- 중요한 이유
  - 변경 영향 범위 축소: 이메일 템플릿 변경 시 EmailService만 수정
  - 테스트 용이: 각 클래스를 독립적으로 단위 테스트 가능
  - 가독성·협업 향상: 클래스 역할이 명확하여 코드 이해·리뷰가 쉬움
  - 재사용성: EmailService를 다른 도메인에서도 재사용 가능

## [COMMON-165] 의존성 역전 원칙이 무엇이고, 어떤 장점이 있는지 설명해 주세요.

답변:

- 의존성 역전 원칙 (Dependency Inversion Principle, DIP)
  - 고수준 모듈(비즈니스 로직)은 저수준 모듈(DB, 외부 API)에 직접 의존하지 않아야 함
  - 둘 다 추상화(인터페이스)에 의존하고, 구체 구현은 추상화에 의존
  - "역전" = 전통적으로 상위가 하위 구현에 의존하던 방향이, 추상화를 통해 뒤집힘
- 예시
  - OrderService가 MySQLRepository를 직접 사용 (X)
  - OrderService → OrderRepository(인터페이스) ← MySQLRepository (O)
- 장점
  - 결합도 감소: DB를 PostgreSQL로 교체해도 OrderService 코드 변경 불필요
  - 테스트 용이: Mock Repository를 주입하여 DB 없이 단위 테스트 가능
  - 확장성: 새 저장소 구현체 추가 시 기존 코드 수정 없이 확장 (OCP와 연계)
  - 유연한 아키텍처: 인프라 계층 교체·변경이 비즈니스 로직에 영향을 주지 않음

## [COMMON-166] 인터페이스를 사용하는 이유와 장단점을 설명해 주세요.

답변:

- 인터페이스 (Interface)
  - 클래스가 반드시 구현해야 하는 메서드 시그니처(계약)를 정의하는 추상 타입
  - "무엇을 할 수 있는지"만 선언하고, 구현은 각 클래스에 위임
- 사용하는 이유
  - 다형성: 동일 인터페이스로 여러 구현체를 교체·확장 가능
  - 결합도 감소: 구체 클래스가 아닌 추상 타입에 의존 (DIP)
  - 테스트: Mock/Stubs 구현체로 외부 의존성 격리
  - 계약 명시: API 스펙을 코드 수준에서 강제
- 장점
  - 유연한 설계, 구현체 교체 용이
  - 다중 구현 가능 (Java 등에서 다중 상속 대안)
  - 팀 협업 시 인터페이스 먼저 정의 → 병렬 개발 가능
- 단점
  - 추상화 계층 증가 → 코드 복잡도·파일 수 증가
  - 과도한 인터페이스 분리 시 오히려 이해 비용 상승
  - 인터페이스 변경 시 모든 구현체 수정 필요 → 초기 설계 신중히 필요

## [COMMON-167] 추상 클래스와 인터페이스의 차이에 대해 설명해 주세요.

답변:

- 추상 클래스 (Abstract Class)
  - 공통 필드·메서드 구현 + 추상 메서드를 함께 가질 수 있는 클래스
  - 단일 상속만 가능 (Java, C# 기준)
  - IS-A 관계, 공통 상태·로직이 있는 밀접한 클래스 그룹에 적합
  - 생성자, protected 필드, 구현된 메서드 포함 가능
- 인터페이스 (Interface)
  - 순수하게 "계약(메서드 시그니처)"만 정의, 상태(필드) 없음 (Java 8+ default method 예외)
  - 다중 구현(implements) 가능
  - CAN-DO 관계 (예: Runnable, Serializable)
  - 서로 다른 계층의 클래스가 같은 행위를 공유할 때 적합
- 선택 기준
  - 공통 구현 코드·상태가 필요 → 추상 클래스
  - 여러 타입에 동일 행위만 강제 → 인터페이스
  - 다중 타입 계약 필요 → 인터페이스
  - 밀접한 클래스 계층, 템플릿 메서드 패턴 → 추상 클래스

## [COMMON-168] 디자인 패턴이 무엇이고, 왜 사용하는지 설명해 주세요.

답변:

- 디자인 패턴 (Design Pattern)
  - 소프트웨어 설계에서 반복적으로 발생하는 문제에 대한 검증된 해결책(템플릿)
  - 특정 코드가 아니라, 클래스·객체 간 관계와 역할 분배의 설계 아이디어
  - GoF(Gang of Four) 패턴: 생성(Creational), 구조(Structural), 행위(Behavioral) 3가지 분류
- 사용하는 이유
  - 공통 언어: "Singleton", "Observer" 등으로 팀 간 설계 의도를 빠르게 전달
  - 검증된 구조: 이미 수많은 프로젝트에서 검증된 방식 → 설계 실수 감소
  - 유지보수·확장성: 변경에 유연한 구조를 체계적으로 적용
  - 문제-해결 매핑: 특정 상황(객체 생성, 알고리즘 교체, 이벤트 전파 등)에 맞는 패턴 선택 가능
- 주의점
  - 패턴을 위해 패턴을 쓰면 과설계 → 실제 문제가 있을 때 적용
  - 패턴 이름만 외우기보다, 어떤 문제를 해결하는지 이해하는 것이 중요

## [COMMON-169] Singleton Pattern이 무엇이고, 장단점은 무엇인지 설명해 주세요.

답변:

- Singleton Pattern
  - 클래스의 인스턴스가 프로그램 전체에서 단 하나만 존재하도록 보장하는 생성 패턴
  - 전역 접근점(getInstance 등)을 제공하여 어디서든 동일 인스턴스에 접근
- 사용 상황
  - DB Connection Pool, Logger, Configuration Manager 등 공유 리소스 관리
  - 인스턴스가 하나여야 하는 경우 (설정, 캐시 매니저)
- 장점
  - 메모리 절약: 인스턴스 하나만 생성
  - 전역 상태 공유: 설정값, 연결 등을 일관되게 관리
- 단점
  - 전역 상태 → 숨은 의존성, 테스트 어려움 (Mock 교체 불가)
  - 멀티스레드 환경에서 동시 생성 문제 → 동기화 필요
  - SRP 위반 가능: 인스턴스 생성 제어 + 비즈니스 로직이 한 클래스에
  - 결합도 증가: getInstance() 호출로 어디서든 접근 → DI(의존성 주입) 방식이 더 선호됨

## [COMMON-170] Factory Method Pattern이 무엇이고, 어떤 상황에서 사용할 수 있는지 설명해 주세요.

답변:

- Factory Method Pattern
  - 객체 생성 로직을 서브클래스(또는 팩토리)에 위임하는 생성 패턴
  - 클라이언트는 구체 클래스를 직접 new하지 않고, 팩토리 메서드를 통해 객체를 받음
  - "어떤 클래스를 생성할지"는 팩토리 서브클래스가 결정
- 구조
  - Creator(추상): createProduct() 팩토리 메서드 선언
  - ConcreteCreator: createProduct()에서 구체 Product 반환
  - Product(추상) / ConcreteProduct: 생성될 객체
- 사용 상황
  - 생성할 객체 타입이 런타임에 결정될 때 (예: OS별 UI 컴포넌트)
  - 객체 생성 과정이 복잡하여 한 곳에 캡슐화하고 싶을 때
  - 클라이언트와 구체 클래스 간 결합을 줄이고 싶을 때 (OCP, DIP)
  - 예: PaymentFactory → createPayment() → CreditCardPayment / KakaoPay

## [COMMON-171] Strategy Pattern이 무엇이고, 어떤 문제를 해결할 수 있는지 설명해 주세요.

답변:

- Strategy Pattern
  - 알고리즘(전략)을 캡슐화하여 런타임에 교체 가능하게 만드는 행위 패턴
  - Context가 Strategy 인터페이스에 의존하고, 구체 전략 구현체를 주입·교체
- 해결하는 문제
  - if-else/switch로 알고리즘 분기 → 새 알고리즘 추가 시 기존 코드 수정 (OCP 위반)
  - 알고리즘과 사용하는 클래스가 강하게 결합
- 구조
  - Strategy(인터페이스): execute() 등 공통 메서드
  - ConcreteStrategy: 각 알고리즘 구현
  - Context: Strategy를 보유, 필요 시 setStrategy()로 교체
- 예시
  - 할인 정책: PercentageDiscount, FixedAmountDiscount, NoDiscount
  - 정렬: QuickSort, MergeSort를 Strategy로 교체
  - 결제: CardStrategy, TransferStrategy
- 장점: OCP 준수, 알고리즘 독립 테스트, 런타임 전략 변경

## [COMMON-172] Observer Pattern이 무엇이고, 어떤 상황에서 사용할 수 있는지 설명해 주세요.

답변:

- Observer Pattern
  - Subject(관찰 대상)의 상태 변경 시, 등록된 Observer(관찰자)들에게 자동으로 알림을 보내는 행위 패턴
  - 일대다(one-to-many) 의존성: Subject 변경 → 모든 Observer가 업데이트
- 구조
  - Subject: Observer 등록(attach), 해제(detach), 변경 알림(notify)
  - Observer: update() 메서드로 Subject 변경에 반응
- 사용 상황
  - 이벤트 기반 UI: 버튼 클릭 → 여러 리스너 반응
  - MVC: Model 변경 → View 자동 갱신
  - Pub/Sub, Message Queue의 기초 개념
  - 예: 주문 상태 변경 → 이메일 발송, SMS 알림, 재고 업데이트, 로그 기록
- 장점
  - Subject와 Observer 느슨한 결합 → Observer 추가·제거 용이
  - 런타임에 구독 관계 동적 변경 가능
- 단점
  - Observer가 많으면 notify 비용 증가
  - 알림 순서·순환 참조 주의

## [COMMON-173] MVC 패턴이 무엇이고, 각 구성 요소의 역할을 설명해 주세요.

답변:

- MVC (Model-View-Controller)
  - UI와 비즈니스 로직을 분리하는 아키텍처 패턴
  - 사용자 입력 → Controller → Model 갱신 → View 갱신 흐름
- Model
  - 데이터와 비즈니스 로직 담당
  - 상태 변경 시 Observer 등으로 View에 알림
  - View, Controller에 대한 의존 없음 (독립적)
- View
  - 사용자에게 데이터를 표시하는 UI
  - Model의 상태를 렌더링, 사용자 입력을 Controller에 전달
  - 비즈니스 로직 포함하지 않음
- Controller
  - 사용자 입력(클릭, 요청)을 받아 해석
  - Model을 업데이트하거나 조회하고, 적절한 View를 선택·갱신
  - View와 Model 사이의 중재자 역할
- 변형
  - MVP, MVVM: View와 Model 간 결합을 더 줄인 변형
  - Web MVC: Spring MVC, Rails 등에서 Controller가 HTTP 요청 처리

## [COMMON-174] Layered Architecture가 무엇이고, 어떤 장단점이 있는지 설명해 주세요.

답변:

- Layered Architecture (계층형 아키텍처)
  - 시스템을 수평 계층(레이어)으로 나누어, 각 계층이 특정 책임만 담당하는 구조
  - 일반적으로 Presentation → Business/Service → Persistence/Data → Database 순
  - 상위 계층은 바로 아래 계층에만 의존 (단방향)
- 각 계층 역할
  - Presentation: UI, API Controller, 사용자 요청·응답 처리
  - Business/Service: 도메인 로직, 유스케이스 실행
  - Persistence: Repository, DAO — DB 접근
  - Database: 실제 데이터 저장
- 장점
  - 관심사 분리: 각 계층 역할이 명확
  - 유지보수·테스트 용이: 계층별 독립 수정·테스트
  - 팀 분업: 프론트/백/DB 담당 분리 가능
  - 표준적 구조 → 학습·온보딩 용이
- 단점
  - 계층 간 호출 오버헤드 (특히 깊은 계층)
  - 전체 흐름 파악 시 여러 계층을 거쳐야 함
  - 성능-critical 경로에서 불필요한 추상화 가능
  - 잘못 설계 시 Anemic Domain Model(로직이 Service에만 몰림) 발생

## [COMMON-175] 관심사의 분리가 무엇이고, 좋은 코드 구조에 왜 중요한지 설명해 주세요.

답변:

- 관심사의 분리 (Separation of Concerns, SoC)
  - 프로그램을 서로 다른 "관심사"(기능·책임) 단위로 나누어, 각 부분이 하나의 관심사만 다루도록 하는 설계 원칙
  - 예: UI 렌더링, 비즈니스 규칙, DB 접근, 인증, 로깅을 각각 분리
- 중요한 이유
  - 변경 격리: DB 변경 시 Repository만, UI 변경 시 View만 수정
  - 가독성: 한 파일·클래스가 하나의 역할만 → 이해하기 쉬움
  - 테스트: 관심사별로 독립적 단위 테스트 작성 가능
  - 재사용: EmailService, AuthService 등을 여러 기능에서 재사용
  - 협업: 팀원이 담당 관심사 영역만 집중 가능
- 적용 예
  - MVC, Layered Architecture, Hexagonal Architecture
  - SRP(Single Responsibility Principle)와 밀접한 관계
  - Controller에 SQL 작성, Entity에 UI 로직 혼재 → SoC 위반

## [COMMON-176] 결합도와 응집도가 무엇이고, 좋은 설계에서는 각각 어떻게 관리되어야 하는지 설명해 주세요.

답변:

- 결합도 (Coupling)
  - 모듈·클래스 간 의존 정도
  - 한 모듈 변경 시 다른 모듈에 미치는 영향 범위
  - 높을수록: 변경 전파 쉬움, 테스트·재사용 어려움
  - 낮을수록: 독립적 변경·테스트 가능 (목표)
- 응집도 (Cohesion)
  - 하나의 모듈·클래스 내부 요소들이 얼마나 밀접하게 관련되어 있는지
  - 높을수록: 하나의 명확한 목적, 이해·유지보수 용이 (목표)
  - 낮을수록: 서로 무관한 기능이 한 곳에 → SRP 위반
- 좋은 설계
  - 높은 응집도 + 낮은 결합도
  - 관련 기능은 한 모듈에 모으고(응집), 모듈 간에는 인터페이스로 느슨하게 연결(결합)
- 관리 방법
  - 결합도 낮추기: DIP, 인터페이스, DI, 이벤트 기반 통신
  - 응집도 높이기: SRP, 도메인별 패키지 분리, Feature 단위 모듈화
  - God Class, 순환 의존 → 결합도 높음, 응집도 낮음의 전형적 안티패턴

## [COMMON-177] 테스트 코드가 필요한 이유와 단위 테스트, 통합 테스트의 차이를 설명해 주세요.

답변:

- 테스트 코드가 필요한 이유
  - 회귀(Regression) 방지: 기능 추가·수정 시 기존 동작 깨짐 조기 발견
  - 리팩토링 안전망: 테스트 통과를 확인하며 구조 개선 가능
  - 설계 개선: 테스트하기 어려운 코드 → 결합도 높음 신호 → 설계 개선 유도
  - 문서화: 테스트가 코드의 의도·사용법을 예시로 보여줌
  - 배포 신뢰: CI에서 자동 실행 → 배포 전 품질 검증
- 단위 테스트 (Unit Test)
  - 가장 작은 단위(함수, 클래스, 메서드)를 독립적으로 테스트
  - 외부 의존성(DB, API)은 Mock/Stub으로 격리
  - 빠르고, 실패 시 원인 특정 용이
  - 예: DiscountCalculator.calculate()가 10% 할인을 올바르게 계산하는지
- 통합 테스트 (Integration Test)
  - 여러 모듈·계층이 함께 동작하는지 테스트
  - 실제 DB, API, 파일 시스템 등과 연동
  - 단위 테스트보다 느리지만, 모듈 간 연동 오류 발견
  - 예: OrderService → Repository → DB 전체 흐름 검증
- 테스트 피라미드: 단위 테스트(많음) → 통합 테스트(중간) → E2E(적음)

## [COMMON-178] 리팩토링이 무엇이고, 리팩토링 시 주의해야 할 점을 설명해 주세요.

답변:

- 리팩토링 (Refactoring)
  - 외부 동작(기능)은 변경하지 않고, 코드 내부 구조만 개선하는 작업
  - 가독성, 유지보수성, 확장성 향상이 목적
  - Martin Fowler: "겉으로 보이는 동작은 그대로, 내부 설계만 개선"
- 대표적 리팩토링 기법
  - Extract Method, Rename, Move Method
  - Replace Conditional with Polymorphism (Strategy)
  - Introduce Interface, DI 적용
- 주의해야 할 점
  - 테스트 없이 리팩토링 금지 → 회귀 버그 위험, 테스트 먼저 확보
  - 한 번에 너무 많은 변경 → 작은 단위로 점진적 수행, 커밋 단위 분리
  - 기능 추가와 리팩토링 혼합 지양 → 별도 PR/커밋으로 분리
  - 성능-critical 코드는 프로파일링 후 신중히 진행
  - 팀과 커뮤니케이션: 대규모 구조 변경은 사전 공유
  - "리팩토링" 명목의 무의미한 변경(변수명만 바꾸기 반복) 지양

## [COMMON-179] 기술 선택 시 trade-off를 설명한다는 것은 어떤 의미인지 설명해 주세요.

답변:

- Trade-off (트레이드오프)
  - 하나의 기술·설계를 선택하면 얻는 이점과 포기하는 단점이 함께 존재한다는 개념
  - "완벽한 선택"은 없고, 상황에 맞는 "균형점"을 찾는 것
- 설명한다는 것의 의미
  - 면접·의사결정에서 "A를 선택했다"만 말하는 것이 아니
  - A의 장점 + A의 단점(또는 B를 포기한 이유) + 왜 그 균형이 우리 상황에 맞는지를 함께 설명
- 예시
  - Monolith vs MSA: MSA는 확장성·독립 배포 장점, 운영 복잡도·분산 트랜잭션 단점
  - SQL vs NoSQL: SQL은 ACID·JOIN, NoSQL은 수평 확장·스키마 유연성
  - Redis 캐시: 응답 속도 향상 vs 캐시 일관성·메모리 비용
- 좋은 trade-off 설명 구조
  - 선택지 나열 → 각각 장단점 → 프로젝트 제약(팀 규모, 트래픽, 일정) → 최종 선택과 이유

## [COMMON-180] 본인의 프로젝트에서 기술적 의사결정을 설명할 때 어떤 구조로 답변하면 좋을지 설명해 주세요.

답변:

- STAR + Trade-off 구조를 기반으로, 기술면접에서 설득력 있게 답변
- 1. 문제 상황 (Situation)
  - 어떤 프로젝트에서, 어떤 기술적 문제·요구사항이 있었는지
  - 예: "일일 10만 건 주문 처리, 피크 시간 응답 지연 발생"
- 2. 선택지와 Trade-off (Task / Options)
  - 고려한 기술·설계 대안 2~3가지와 각각의 장단점
  - 예: "동기 처리 유지 vs 메시지 큐 도입 vs 캐시 레이어 추가"
- 3. 결정과 이유 (Action)
  - 최종 선택과, 프로젝트 제약(일정, 팀 역량, 트래픽)을 고려한 근거
  - 예: "Kafka 도입 — 비동기 처리로 응답 시간 단축, 팀에 Kafka 경험자 있음"
- 4. 결과 (Result)
  - 정량적 지표: 응답 시간 500ms → 80ms, 처리량 3배 증가
  - 정성적 효과: 장애 격리, 배포 독립성 등
- 5. 아쉬운 점 / 배운 점 (Reflection)
  - "모니터링 구축이 늦어 장애 대응에 어려움 → 다음에는 Observability 먼저 설계"
  - 회고 내용을 포함하면 성장 가능성 어필
- 핵심: "무엇을 선택했는지"보다 "왜 그 선택이 합리적이었는지"를 trade-off와 함께 설명
