## [COMMON-081] OSI 7계층과 TCP/IP 4계층을 비교해 설명해 주세요.

답변: OSI 7계층은 네트워크 통신 과정을 7게의 계층으로 나누어 설명하는 참조 모델입니다.

- 물리 계층, 데이터 링크 계층, 네트워크 계층, 전송 계층, 세션 계층, 표현 계층, 응용 계층으로 구성됩니다.

TCP/IP 4계층은 실제 인터넷 프로토콜 구조에 더 가까운 모델로 보통 네트워크 액세스 계층, 인터넷 계층, 전송 계층, 응용 계층으로 나뉩니다.
OSI의 물리/데이터 링크 계층은 TCP/IP의 네트워크 계층에, OSI의 세션/표현/응용 계층은 TCP/IP의 응용 계층에 대응됩니다.

그래서 OSI 계층은 네트워크 이해를 위한 이론적 모델에 가깝고, TCP/IP 4계층은 실제 인터넷에서 사용되는 프로토콜 구조를 설명하기에 더 적합하다고 알고 있습니다.

## [COMMON-082] TCP와 UDP의 차이에 대해 설명해 주세요.

답변: TCP는 연결 지향형 프로토콜입니다. 데이터를 보내기 전에 연결을 설정하고, 데이터가 순서대로 도착했는지 확인하면서 손실된 데이터는 재전송하는 구조입니다. 그래서 신뢰성이 필요한 파일 전송이나 웹통신, 이메일 등에 적합하다고 알고 있습니다.

반면에 UDP는 비연결형 프로토콜로 연결 설정 과정 없이 데이터를 보내고, 전달 보장이나 순서 보장을 기본적으로 제공하지 않습니다. 대신 TCP보다 구조가 단순하고 오버헤드가 작아, 실시간 스트리밍처럼 빠른 전송이 중요한 경우 사용됩니다.

TCP: 신뢰성 / UDP: 속도, 단순

## [COMMON-083] TCP 3-way handshake가 무엇이고, 왜 필요한지 설명해 주세요.

답변: TCP 3-way handshake는 TCP 연결을 시작하기 위해 클라이언트와 서버가 세 번의 패킷 교환을 수행하는 과정입니다.

먼저 클라이언트가 서버에게 연결 요청인 SYN을 보냅니다. 그리고 서버는 요청을 수락한다는 의미로 SYN과 ACK를 함께 보낸 후에 클라이언트가 ACK를 보내면 연결이 성립됩니다.

이 과정이 필요한 이유는 양쪽이 서로 통신 가능한 상태인지 확인하고, 초기 순서 번호를 교환하기 위해서라고 알고 있습니다. TCP의 경우 신뢰성 있는 스트림 전송을 제공해야 하기 때문에 데이터를 보내기 전에 연결 상태와 순서 제어에 필요한 정보를 맞춰야 하는 것으로 알고 있습니다.

## [COMMON-084] TCP 4-way handshake가 무엇이고, 연결 종료 과정에서 TIME_WAIT이 필요한 이유를 설명해 주세요.

답변: TCP 4-way handshake는 TCP 연결을 종료할 때 사용하는 절차입니다. TCP는 양방향 통신이라 한쪽이 데이터를 다 보냈다고 반대쪽도 종료되는 구조가 아닙니다.

먼저 연결을 종료하려는 쪽에서 FIN을 보내고, 상대방이 ACK를 보내게 됩니다. 이후에 상대방도 보낼 데이터가 끝나면 FIN을 보내고, 처음 종료를 요청한 쪽에서 ACK를 보내면서 연결이 종료됩니다.

TIME_WAIT의 경우에는 마지막 ACK를 보낸 쪽에서 일정 시간 동안 연결 정보를 유지하는 상태입니다.
이 시간이 필요한 이유는 마지막 ACK가 손실되었을 때 상대방이 FIN을 재전송할 수 있기 때문입니다. 또 이전 연결에서 지연된 패킷이 새로운 연결에 영향을 주지 않도록 하기 위한 목적도 있습니다.

## [COMMON-085] TCP의 신뢰성 보장 방법에 대해 설명해 주세요.

답변:

- 순서 번호를 사용해 데이터의 순서를 관리
- 수신자는 받은 데이터에 대해 ACK를 보내고
- 송신자는 ACK를 받지 못한 데이터가 있으면 재전송
- 체크섬을 통해 데이터 손상 여부를 확인
- 흐름 제어를 통해 수신자가 처리할 수 있는 양만큼 데이터를 보내도록 조절
- 혼잡 제어도 TCP에서 중요 -> 네트워크가 혼잡하다고 판단되면 송신 속도를 줄여 패킷 손실과 네트워크 붕괴 방지

순서 제어, ACK 재전송, 체크섬, 흐름 제어, 혼잡 제어를 통해 신뢰성 보장

## [COMMON-086] HTTP가 무엇이고, HTTP의 특징을 설명해 주세요.

답변: HTTP는 Hypertext Transfer Protocol의 약자로, 웹에서 클라이언트와 서버가 데이터를 주고 받기 위한 응용 계층 프로토콜입니다.

클라이언트가 서버에게 요청을 보내면, 서버는 그 요청에 대한 응답을 반환하는 구조를 가집니다.
HTTP 메시지는 메서드, URI, 헤더, 본문을 통해서 요청의 의도와 데이터를 표현합니다.
또 기본적으로 Stateless한 프로토콜이라서, 각각의 요청을 독립적으로 처리하고, 이전 요청 상태를 자동으로 기억하지 않습니다.
그래서 필요한 경우 쿠키나 세션, 토큰 등을 사용해서 상태를 관리합니다.

## [COMMON-087] HTTP와 HTTPS의 차이에 대해 설명해 주세요.

답변: 보안 계층 유무입니다. HTTP는 데이터를 암호화하지 않고 전송해서 데이터를 중간에서 가로채면 내용을 볼 수 있는데 HTTPS는 TLS를 적용해서 클라이언트와 서버 사이의 통신을 암호화합니다.

## [COMMON-088] TLS/SSL Handshake가 어떤 역할을 하는지 설명해 주세요.

답변: TLS Handshake는 클라와 서버가 안전한 통신을 시작하기 전에 암호화 방식과 키를 협상하는 과정입니다.

핸드셰이크 과정에서 클라와 서버는 사용할 TLS 버전, 암호화 알고리즘, 키 교환 방식을 결정하는 데요.
서버는 인증서를 통해 자신의 신원을 증명하고, 양쪽은 이후 실제 데이터 암호화에 사용할 세션 키를 생성합니다.

그래서 TLS 핸드셰이크의 역할은 상대방을 인증하고, 안전한 암호화 통신에 필요한 공통 키를 합의하는 과정입니다.
이 과정 후에 HTTP 데이터는 합의된 키를 사용해 암호화돼서 전송됩니다.

## [COMMON-089] DNS가 무엇이고, 도메인 이름이 IP 주소로 변환되는 과정을 설명해 주세요.

답변: DNS는 도메인 네임 시스템의 약자로 사람이 읽기 쉬운 도메인 이름을 IP 주소로 변환하는 시스템입니다.

사용자가 브라우저에 도메인을 입력하면, 브라우저나 운영체제 캐시를 확인하고, 캐시에 없다면 DNS Resolver에 질의하고, Resolver는 Root DNS, TLD DNS, Authoritative DNS 서버를 순서대로 조회해서 IP 주소를 얻습니다.

이후 클라는 얻은 IP 주소를 사용해서 서버와 TCP 연결을 맺고, HTTP 또는 HTTPS에 요청을 보냅니다.

## [COMMON-094] Cookie, Session, Token의 차이에 대해 설명해 주세요.

## [COMMON-095] Stateless하다는 것이 무엇이고, HTTP가 Stateless한 것이 어떤 장단점을 가지는지 설명해 주세요.

답변: Stateless란 서버가 이전 요청의 상태를 기억하지 않고, 각 요청을 독립적으로 처리하는 것입니다.

HTTP는 기본적으로 Stateless한 프로토콜로 서버가 각 요청만 보고 처리할 수 있어야 되며, 이전 요청과의 연결 상태를 자동으로 유지하지 않습니다.

그래서 서버 확장이 쉽습니다. 요청 간의 상태를 서버가 직접 유지하지 않으면 여러 서버가 요청을 나누어 처리하기 쉽습니다. 다만, 로그인 상태나 장바구니처럼 사용자 상태가 필요한 기능을 구현하기 위해서 별도의 쿠키, 세션, 토큰 같은 상태 관리 방식이 필요합니다.

## [COMMON-096] CORS가 무엇이고, 왜 발생하는지 설명해 주세요.

답변: Cross Origin Resource Sharing의 약자로 브라우저가 다른 출처의 리소스에 접근할 수 있는지 서버의 허용 정책을 확인하는 매커니즘입니다.

웹 브라우저는 보안 떄문에 기본적으로 Same-Origin Policy를 적용하는데, 프로토콜, 도메인, 포트가 다른 출처로 요청을 보낼 때 제한을 둡니다. 하지만 실제 웹 서비스에서는 프론트나 백엔드 도메인이 다른 경우가 많아서, 서버가 특정 출처의 요청을 허용하도록 응답 헤더에 포함합니다.

그래서 CORS 오류는 보통 브라우저가 다른 출처로 요청을 보냈지만, 서버 응답에 적절한 `Access-Control-Allow-Origin` 같은 CORS 허용 헤더가 없을 때 발생합니다.

## [COMMON-097] Blocking / Non-blocking과 Synchronous / Asynchronous의 차이에 대해 설명해 주세요.

답변:

- Blocking: 자신의 작업을 진행하다가 다른 주체의 작업이 시작되면 다른 작업이 끝날 때까지 기다렸다가 자신의 작업을 시작하는 것.
- Non-blocking: 다른 주체의 작업에 관련 없이 자신의 작업을 진행
- Synchronous: 요청이 들어온 순서에 맞게 하나씩 처리
- Asynchronous: 하나의 요청이 끝나기 전에도 다른 요청을 동시에 처리 가능(콜백, 이벤트)

Blocking vs Non-blocking: 완료될 때까지 기다리는가
Sync vs Async: 결과를 처리하는 흐름이 어떻게 구성되는가

## [COMMON-098] I/O Multiplexing이 무엇이고, 왜 필요한지 설명해 주세요.

답변: I/O 멀티플렉싱은 하나의 스레드나 프로세스가 여러 I/O 이벤트를 동시에 감시하고, 준비된 I/O만 처리할 수 있게 하는 방식입니다.

네트워크 서버에서 클라이언트 연결마다 스레드를 하나씩 만들면 연결 수가 많아질수록 스레드 생성 비용, 메모리 사용량, 컨텍스트 스위칭 비용이 커집니다.
그래서 I/O 멀티플렉싱으로 여러 소켓을 감시하다가 읽기나 쓰기가 가능한 소켓만 처리할 수 있도록 합니다.

- 시스템 호출 `select`, `poll`, `epoll`

## [COMMON-099] WebSocket이 무엇이고, HTTP와 어떤 차이가 있는지 설명해 주세요.

답변: 웹 소캣은 클라이언트와 서버 사이에 지속적인 양방향 통신 채널을 제공하는 프로토콜입니다.

HTTP의 경우 기본적으로 클라이언트가 요청을 보내고 서버가 응답하는 요청-응답 구조인데요, 웹소캣은 한 번 연결이 되면 클라이언트와 서버가 연결을 유지하면서 서로 데이터를 주고 받습니다.

그래서 채팅이나 실시간 알림처럼 서버가 클라이언트에게 즉각 데이터를 전달할 때 주로 사용하는 것으로 알고 있습니다.

## [COMMON-100] Load Balancing이 무엇이고, 어떤 방식들이 있는지 설명해 주세요.

답변: 로드밸런싱은 여러 서버에 요청을 분산시켜서 부하가 집중되지 않게하고 가용성과 확장성을 높이는 방식입니다. 특정 서버에 장애가 발생했을 때도 정상 서버로 요청을 보내도록 할 수 있습니다.

대표적으로 Round Robin, Least Connections, IP Hash, Weighted Round Robin 등이 있습니다.

- Round Robin: 서버에 순서대로 요청 분배
- Least Connections: 현재 연결 수가 가장 적은 서버에 요청 보냄
- IP Hash: 클라이언트 IP 기준으로 특정 서버에 요청을 보내 세션 고정이 필요한 경우 활용

## [COMMON-101] TCP의 흐름 제어와 혼잡 제어의 차이에 대해 설명해 주세요.

답변:

- 흐름 제어: 송신자가 수신자의 처리 능력을 초과해 데이터를 보내지 않도록 조절하는 기능. 자신이 받을 수 있는 버퍼 크기를 알려주고, 송신자는 그 범위 안에서 데이터를 보냄
- 혼잡 제어: 네트워크 전체의 혼잡 상태를 고려해 송신 속도를 조절하는 기능. 네트워크에 패킷이 너무 많이 몰리면 손실과  지연이 발생하기에 TCP는 혼잡 윈도우를 조절하며 전송량 제어.
- 흐름 제어 -> 수신자 보호
- 혼잡 제어 -> 네트워크 보호
