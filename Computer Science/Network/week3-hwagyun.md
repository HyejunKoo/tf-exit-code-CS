## [COMMON-081] OSI 7계층과 TCP/IP 4계층을 비교해 설명해 주세요.

답변:

OSI 7계층은 네트워크 통신 과정을 개념적 관점에서 나눈 7개의 계층 구조로, 물리/데이터링크/네트워크/전송/세션/표현/응용계층으로 이루어져 있습니다.

이에 반해 TCP/IP 4계층은 실제 인터넷 통신에 사용되는 프로토콜을 중심으로 나눈 계층 구조로, 네트워크 액세스/인터넷/전송/응용계층으로 이루어져 있습니다.

OSI 7계층의 물리계층과 데이터링크계층은 TCP/IP의 네트워크 액세스계층에 대응하고, 네트워크계층은 인터넷계층, 전송계층은 전송계층에 대응합니다. 또한 OSI의 세션/표현/응용계층은 TCP/IP에서는 응용계층 하나로 표현됩니다.

## [COMMON-082] TCP와 UDP의 차이에 대해 설명해 주세요.

답변:

TCP는 데이터를 전송하기 전에 송신자와 수신자 간 연결을 설정하고, 데이터가 정상적으로 전달되었는지 ACK를 통해 확인하는 전송계층 프로토콜입니다.

데이터가 유실되거나 정상적으로 전달되지 않은 경우 재전송하며, 순서 제어와 흐름 제어, 혼잡 제어 등을 통해 데이터의 신뢰성을 보장합니다. 다만 이러한 과정으로 인해 UDP보다 상대적으로 처리 비용과 지연이 커질 수 있습니다.

UDP는 TCP와 달리 연결을 설정하거나 데이터의 정상적인 수신 여부를 확인하지 않고 데이터그램을 전송하는 비연결형 프로토콜입니다. 재전송이나 순서 보장을 기본적으로 제공하지 않기 때문에 신뢰성은 상대적으로 낮지만, 처리 과정이 단순하여 빠른 전송이 필요한 실시간 스트리밍, 음성 통화, 온라인 게임 등에 주로 사용됩니다.

## [COMMON-083] TCP 3-way handshake가 무엇이고, 왜 필요한지 설명해 주세요.

답변:

TCP 3-way handshake는 TCP 통신을 시작하기 전에 클라이언트와 서버가 서로 통신 가능한 상태인지 확인하고, 초기 순서 번호를 교환하여 연결을 설정하는 과정입니다.

본 통신 과정이 3-way라고 불리는 이유는 클라이언트와 서버의 연결 설정 과정이 세 번의 패킷 교환으로 이루어지기 때문입니다.

먼저 클라이언트가 서버에 SYN 패킷을 보내 연결을 요청합니다. 서버는 클라이언트의 요청에 대한 ACK와 서버 측의 연결 요청을 의미하는 SYN을 함께 보냅니다. 마지막으로 클라이언트가 서버의 SYN에 대한 ACK를 보내면 연결이 설정됩니다.

이 과정을 통해 양쪽이 데이터를 송수신할 수 있는 상태인지 확인하고, 이후 데이터의 순서를 관리하기 위한 초기 순서 번호를 동기화할 수 있습니다.

## [COMMON-084] TCP 4-way handshake가 무엇이고, 연결 종료 과정에서 TIME_WAIT이 필요한 이유를 설명해 주세요.

답변:

TCP 4-way handshake는 TCP 통신을 마친 후 양측의 연결을 정상적으로 종료할 때 사용하는 과정입니다.

통신 과정이 4-way라고 불리는 이유는 클라이언트와 서버의 연결 종료 과정이 일반적으로 네 번의 패킷 교환으로 이루어지기 때문입니다.

먼저 클라이언트가 FIN 플래그를 통해 더 이상 보낼 데이터가 없으며 연결을 종료하겠다는 신호를 보냅니다. 서버는 해당 메시지를 수신했다는 ACK를 보내고, 아직 서버에서 보낼 데이터가 남아 있다면 전송을 계속합니다.

서버의 데이터 전송이 모두 끝나면 서버도 FIN을 클라이언트에게 전송합니다. 마지막으로 클라이언트가 서버의 FIN을 확인했다는 ACK를 보내면 연결 종료 절차가 완료됩니다.

다만 마지막 ACK를 보낸 클라이언트는 즉시 연결 정보를 제거하지 않고 일정 시간 동안 TIME_WAIT 상태로 대기합니다. 이는 마지막 ACK가 유실된 경우 서버가 FIN을 재전송할 수 있도록 하고, 이전 연결에서 지연된 패킷이 동일한 IP 주소와 포트 번호를 사용하는 새로운 연결에 영향을 주는 것을 방지하기 위해 필요합니다.

TIME_WAIT 시간은 TCP 표준에서 일반적으로 최대 세그먼트 수명인 MSL의 두 배인 2MSL을 기준으로 하며, 실제 시간은 운영체제 구현에 따라 달라질 수 있습니다.

## [COMMON-085] TCP의 신뢰성 보장 방법에 대해 설명해 주세요.

답변:

TCP가 신뢰성을 보장하는 방법에는 순서 보장, 오류 제어, 흐름 제어, 혼잡 제어 등의 기법이 존재합니다.

우선 순서 보장은 데이터 세그먼트에 순서 번호를 부여하여 수신자가 데이터를 올바른 순서대로 재조립할 수 있도록 하는 방법을 의미합니다. 세그먼트가 순서대로 도착하지 않더라도 순서 번호를 기준으로 재정렬한 후 애플리케이션에 전달할 수 있습니다.

다음으로 오류 제어는 송신자가 보낸 데이터에 대해 수신자가 ACK를 반환하고, 일정 시간 안에 ACK가 오지 않거나 데이터 유실이 감지되면 해당 데이터를 재전송하는 방법입니다. TCP는 체크섬을 통해 전송 과정에서 데이터가 손상되었는지도 검사합니다.

흐름 제어는 수신자의 처리 속도보다 송신 속도가 지나치게 빨라 수신 버퍼가 넘치는 것을 방지하는 기법입니다. 수신자가 자신의 수신 가능 크기인 수신 윈도우를 송신자에게 알려 전송량을 조절합니다.

마지막으로 혼잡 제어는 송신자가 네트워크의 혼잡 상태에 맞춰 데이터 전송량을 조절하는 기법입니다. 대표적으로 Slow Start에서는 혼잡 윈도우를 처음에는 작게 시작하여 ACK를 받을 때마다 빠르게 증가시키고, 혼잡 회피 단계에서는 AIMD 방식에 따라 윈도우를 점진적으로 증가시키다가 패킷 손실이 발생하면 감소시킵니다.

## [COMMON-086] HTTP가 무엇이고, HTTP의 특징을 설명해 주세요.

답변:

HTTP는 클라이언트와 서버가 웹상의 리소스를 요청하고 응답하기 위해 사용하는 응용계층 프로토콜입니다.

HTTP의 주요 특징에는 클라이언트-서버 구조, 무상태성, 비연결성 등이 있습니다.
우선 클라이언트-서버 구조는 클라이언트가 서버에 요청을 보내고, 서버가 요청을 처리한 결과를 응답하는 구조를 의미합니다. 클라이언트와 서버의 역할을 분리함으로써 각각 독립적으로 개발하고 확장할 수 있습니다.
다음으로 무상태성은 서버가 기본적으로 이전 요청의 상태를 저장하지 않는다는 의미입니다. 각각의 요청은 독립적으로 처리되기 때문에 서버를 수평적으로 확장하거나 여러 서버에 요청을 분산하기 쉽다는 장점이 있습니다. 다만 로그인 상태와 같이 상태 유지가 필요한 경우에는 쿠키, 세션, 토큰 등을 추가로 사용합니다.
마지막으로 비연결성은 요청과 응답이 끝난 후 연결을 계속 점유하지 않는 특성을 의미합니다. 이를 통해 다수의 클라이언트 요청을 효율적으로 처리할 수 있습니다. 다만 HTTP/1.1에서는 기본적으로 지속 연결을 사용할 수 있고, HTTP/2와 HTTP/3에서도 하나의 연결을 활용하여 여러 요청을 처리할 수 있으므로, 요청마다 반드시 연결을 끊는다고 표현하는 것은 정확하지 않습니다.

## [COMMON-087] HTTP와 HTTPS의 차이에 대해 설명해 주세요.

답변:

HTTP와 HTTPS의 가장 큰 차이는 클라이언트와 서버 사이에서 전송되는 데이터가 TLS를 통해 보호되는지 여부입니다.

HTTP는 웹상의 리소스를 요청하고 응답하기 위한 응용계층 프로토콜입니다. HTTP만 사용하는 경우 전송되는 데이터가 평문으로 노출될 수 있어, 중간에서 패킷을 가로챈 공격자가 요청과 응답 내용을 확인하거나 변조할 가능성이 있습니다.

반면 HTTPS는 HTTP 통신에 TLS를 적용한 방식입니다. TLS Handshake 과정에서 서버 인증서를 사용하여 서버의 신원을 확인하고, 클라이언트와 서버가 세션 키를 안전하게 생성합니다.

이후 실제 HTTP 데이터는 해당 세션 키를 사용하는 대칭키 암호화 방식으로 보호됩니다. 이를 통해 HTTPS는 데이터의 기밀성뿐만 아니라 데이터가 전송 과정에서 변경되지 않았는지를 확인하는 무결성과, 통신 대상 서버가 올바른 서버인지 확인하는 인증 기능을 제공합니다.

## [COMMON-088] TLS/SSL Handshake가 어떤 역할을 하는지 설명해 주세요.

답변:

TLS Handshake는 HTTPS 통신을 시작하기 전에 클라이언트와 서버가 사용할 TLS 버전과 암호화 알고리즘을 협상하고, 서버의 신원을 인증하며, 이후 통신에 사용할 세션 키를 안전하게 생성하는 과정입니다.

먼저 클라이언트는 ClientHello 메시지를 보내 지원 가능한 TLS 버전, 암호화 알고리즘과 키 교환에 필요한 정보를 전달합니다.

서버는 ServerHello를 통해 사용할 TLS 버전과 암호화 알고리즘을 선택하고, 일반적으로 서버 인증서와 키 교환에 필요한 정보를 전달합니다. 클라이언트는 서버 인증서가 신뢰할 수 있는 인증기관에서 발급되었는지, 인증서의 도메인이 접속한 서버와 일치하는지 등을 확인합니다.

이후 클라이언트와 서버는 키 교환 알고리즘을 통해 동일한 세션 키를 생성합니다. 양측은 Finished 메시지를 교환하여 Handshake 과정이 정상적으로 완료되었고 서로 동일한 키를 가지고 있음을 확인합니다.

Handshake가 완료되면 실제 HTTP 데이터는 인증서 자체가 아니라, Handshake 과정에서 생성된 세션 키를 사용하는 대칭키 암호화 방식으로 보호됩니다.

TLS 버전에 따라 구체적인 메시지 순서와 왕복 횟수는 다를 수 있습니다. 특히 TLS 1.2와 TLS 1.3의 Handshake 구조가 다르기 때문에 TLS Handshake가 항상 네 번의 통신으로 구성된다고 단정하는 것은 적절하지 않습니다.

## [COMMON-089] DNS가 무엇이고, 도메인 이름이 IP 주소로 변환되는 과정을 설명해 주세요.

답변:

DNS는 Domain Name System의 줄임말로, 사람이 기억하기 쉬운 도메인 이름을 네트워크 통신에 필요한 IP 주소 등의 정보와 연결해 주는 분산형 계층 구조의 시스템입니다.

사용자가 브라우저에 도메인 이름을 입력하면, 우선 브라우저와 운영체제의 DNS 캐시 및 hosts 파일에 해당 도메인 정보가 있는지 확인합니다.

정보가 없다면 운영체제의 Stub Resolver가 통신사나 회사, 공용 DNS 등으로 설정된 재귀 DNS 리졸버에 질의합니다. 재귀 DNS 리졸버에 이미 캐시된 정보가 있다면 즉시 IP 주소를 반환합니다.

캐시에도 정보가 없다면 재귀 DNS 리졸버가 Root DNS 서버에 질의합니다. Root DNS 서버는 해당 최상위 도메인을 관리하는 TLD DNS 서버의 위치를 알려줍니다.

이후 재귀 DNS 리졸버는 `.com`이나 `.kr`과 같은 TLD DNS 서버에 질의하고, TLD DNS 서버는 해당 도메인의 권한 있는 DNS 서버인 Authoritative DNS 서버의 위치를 알려줍니다.

마지막으로 재귀 DNS 리졸버가 Authoritative DNS 서버에 질의하여 도메인에 대응하는 IP 주소를 받아옵니다. 이 결과는 클라이언트에 반환되며, 재귀 DNS 리졸버는 레코드에 설정된 TTL 동안 해당 정보를 캐싱하여 이후 요청에 더 빠르게 응답합니다.
