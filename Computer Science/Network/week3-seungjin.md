## [COMMON-081] OSI 7계층과 TCP/IP 4계층을 비교해 설명해 주세요.

답변:

OSI 7계층은 ISO가 통신 과정을 개념적으로 나눈 참조 모델이고, TCP/IP 4계층은 실제 인터넷에서 쓰이는 구현 모델입니다. OSI의 1~2계층이 네트워크 액세스, 3계층이 인터넷, 4계층이 전송, 5~7계층이 응용 계층에 대응합니다. 정리하면 OSI는 학습과 설계를 위한 개념 도구이고, 실제 통신은 TCP/IP 스택으로 이루어집니다.

참고 자료:
- https://blog.skby.net/osi-7-layer와-tcp-ip-비교/

## [COMMON-082] TCP와 UDP의 차이에 대해 설명해 주세요.

답변:

TCP는 연결지향 프로토콜로, 데이터를 보내기 전에 연결을 맺고 순서 보장과 재전송으로 신뢰성 있게 전달하지만 그만큼 느립니다. UDP는 비연결형이라 신뢰성은 보장하지 않지만 오버헤드가 적어 빠릅니다. 그래서 정확성이 중요한 웹이나 파일 전송은 TCP를, 속도가 중요한 실시간 스트리밍이나 게임은 UDP를 씁니다.

참고 자료:
- https://velog.io/@hidaehyunlee/TCP-와-UDP-의-차이

## [COMMON-083] TCP 3-way handshake가 무엇이고, 왜 필요한지 설명해 주세요.

답변:

TCP가 데이터를 보내기 전에 연결을 수립하는 3단계 과정입니다. 클라이언트가 SYN을 보내고 서버가 SYN+ACK로 응답한 뒤 클라이언트가 다시 ACK를 보내면 연결이 맺어집니다. 데이터 전송 전에 양쪽이 서로 주고받을 준비가 됐는지 확인하고, 이후 순서 판단의 기준이 되는 초기 시퀀스 번호를 교환하기 위해 필요합니다.

참고 자료:
- https://velog.io/@yeseolee/3-Way-4-Way-HandshakeTCP-연결-설정과-해제

## [COMMON-084] TCP 4-way handshake가 무엇이고, 연결 종료 과정에서 TIME_WAIT이 필요한 이유를 설명해 주세요.

답변:

연결을 끊는 4단계 과정입니다. 끊는 쪽이 FIN을 보내면 상대가 ACK로 답하고, 상대도 데이터를 다 보낸 뒤 FIN을 보내면 마지막으로 ACK를 보내 종료됩니다. 종료를 요청한 쪽은 마지막에 TIME_WAIT으로 잠시 대기하는데, 마지막 ACK가 유실됐을 때 다시 응답하고 이전 연결의 지연 패킷이 새 연결에 섞이는 것을 막기 위해서입니다.

참고 자료:
- https://velog.io/@yeseolee/3-Way-4-Way-HandshakeTCP-연결-설정과-해제

## [COMMON-085] TCP의 신뢰성 보장 방법에 대해 설명해 주세요.

답변:

TCP는 여러 기법을 함께 써서 신뢰성을 보장합니다. 시퀀스 번호로 순서를 맞추고 ACK로 수신을 확인하며, 체크섬으로 오류를 검출하고 유실되면 재전송합니다. 여기에 수신자를 보호하는 흐름 제어와 네트워크를 보호하는 혼잡 제어로 전송량을 조절합니다.

## [COMMON-086] HTTP가 무엇이고, HTTP의 특징을 설명해 주세요.

답변:

HTTP는 웹에서 문서나 데이터를 주고받기 위한 애플리케이션 계층 프로토콜입니다. 클라이언트 요청에 서버가 응답하는 구조이고, 서버가 요청 사이의 상태를 저장하지 않는 무상태 특성이 있어 로그인 유지 같은 건 쿠키나 세션, 토큰으로 따로 처리합니다. 연결은 HTTP/1.1의 keep-alive로 재사용하며 이후 버전에서 성능이 계속 개선돼 왔습니다.

## [COMMON-087] HTTP와 HTTPS의 차이에 대해 설명해 주세요.

답변:

HTTPS는 HTTP에 TLS 암호화 계층을 더한 것으로, 포트도 80이 아닌 443을 씁니다. HTTP는 평문이라 도청과 변조에 취약하지만, HTTPS는 암호화로 기밀성과 무결성을, 인증서로 서버 신원을 보장합니다. 대신 TLS 핸드셰이크가 추가돼 최초 연결이 조금 느립니다.

참고 자료:
- https://velog.io/@dong5854/HTTPS와-SSL인증서-대칭키-공개키비대칭키

## [COMMON-088] TLS/SSL Handshake가 어떤 역할을 하는지 설명해 주세요.

답변:

TLS 핸드셰이크는 암호화 통신을 시작하기 전에 양쪽이 암호 방식을 합의하고 키를 교환하는 과정입니다. 서버 인증서로 신원을 확인하고, 공개키를 이용해 대칭 세션 키를 안전하게 주고받습니다. 이후 실제 데이터는 빠른 대칭 키로 암호화합니다.

## [COMMON-089] DNS가 무엇이고, 도메인 이름이 IP 주소로 변환되는 과정을 설명해 주세요.

DNS는 사람이 읽는 도메인 이름을 IP 주소로 바꿔 주는 시스템입니다. 먼저 캐시를 확인하고, 없으면 재귀 리졸버가 루트 네임서버, TLD 네임서버, 권한 있는 네임서버를 차례로 물어 최종 IP를 얻어 옵니다. 이 결과는 TTL만큼 캐싱해 두고 재사용합니다.

## [COMMON-090] 브라우저에 URL을 입력했을 때 서버 응답을 받기까지의 흐름을 설명해 주세요.

답변:

## [COMMON-091] HTTP 메서드 GET, POST, PUT, PATCH, DELETE의 차이를 설명해 주세요.

답변:

HTTP 메서드는 리소스에 대한 행위를 나타냅니다. GET은 조회, POST는 생성, PUT은 전체 수정, PATCH는 부분 수정, DELETE는 삭제입니다. 이 중 GET은 서버 상태를 바꾸지 않아 안전하고, PUT과 DELETE는 여러 번 보내도 결과가 같아 멱등이지만 POST는 호출할 때마다 리소스가 새로 생겨 멱등이 아닙니다.

참고 자료:
- https://velog.io/@adler/CS-HTTP의-멱등성

## [COMMON-092] HTTP 상태 코드 2xx, 3xx, 4xx, 5xx의 의미를 설명해 주세요.

답변:

응답 코드의 첫 자리가 종류를 나타냅니다. 2xx는 성공, 3xx는 리다이렉션, 4xx는 클라이언트 요청 오류, 5xx는 서버 오류입니다. 대표적으로 200 성공, 404 리소스 없음, 500 서버 오류가 있고, 자주 헷갈리는 401은 인증이 안 된 경우, 403은 인증은 됐지만 권한이 없는 경우입니다.

참고 자료:
- https://velog.io/@otteru/HTTP3-HTTP-상태코드

## [COMMON-093] RESTful API가 무엇인지 설명해 주세요.

답변:

REST는 자원을 URI로 식별하고 그 자원에 대한 행위를 HTTP 메서드로 표현하는 아키텍처 스타일이며, 이 원칙을 따르는 API를 RESTful API라고 합니다. 무상태와 균일한 인터페이스 같은 제약을 두어, 주소와 메서드만 봐도 어떤 자원에 무슨 동작을 하는지 알 수 있는 것이 특징입니다. 다만 실무 API 상당수는 REST 원칙을 완전히 지키지는 않아 엄밀히는 HTTP API에 가깝습니다.

참고 자료:

## [COMMON-094] Cookie, Session, Token의 차이에 대해 설명해 주세요.

답변:

셋 다 무상태인 HTTP에서 사용자를 식별하는 수단인데, 상태를 어디에 저장하느냐가 다릅니다. 쿠키는 브라우저에 저장되는 값이고, 세션은 상태를 서버에 저장한 뒤 클라이언트에는 세션 ID만 내려주는 방식입니다. 토큰은 인증 정보를 토큰 자체에 담아 클라이언트가 보관하므로, 서버가 서명만 검증하면 되어 별도 저장소 없이 확장에 유리합니다.

참고 자료:

## [COMMON-095] Stateless하다는 것이 무엇이고, HTTP가 Stateless한 것이 어떤 장단점을 가지는지 설명해 주세요.

답변:

무상태는 서버가 요청 사이에 클라이언트 상태를 저장하지 않아, 각 요청이 처리에 필요한 정보를 스스로 담는 것을 말합니다. 어떤 서버가 처리해도 결과가 같아 서버를 늘리기 쉽고 장애에 강한 것이 장점입니다. 단점은 인증 정보 같은 걸 요청마다 다시 보내야 하고, 로그인 유지처럼 상태가 필요한 기능은 쿠키나 세션, 토큰으로 따로 구현해야 한다는 점입니다.

참고 자료:
- https://velog.io/@msung99/HTTP

## [COMMON-096] CORS가 무엇이고, 왜 발생하는지 설명해 주세요.

답변:

CORS는 브라우저가 다른 출처의 리소스를 요청할 때 서버가 이를 허가하는 방식입니다. 브라우저는 보안상 스킴, 호스트, 포트 중 하나라도 다른 출처와의 통신을 기본적으로 막는데, 서버가 응답 헤더에 허용 출처를 명시하면 브라우저가 이를 확인하고 통과시킵니다. CORS는 브라우저에서 동작하는 규칙이라 서버끼리의 통신이나 Postman에서는 발생하지 않고, 해결도 서버에서 헤더를 설정해야 합니다.

참고 자료:
- https://evan-moon.github.io/2020/05/21/about-cors/

## [COMMON-097] Blocking / Non-blocking과 Synchronous / Asynchronous의 차이에 대해 설명해 주세요.

답변:

블로킹과 논블로킹은 제어권을 기준으로 나눕니다. 호출한 함수가 끝날 때까지 제어권을 안 돌려주면 블로킹, 바로 돌려받아 다른 일을 할 수 있으면 논블로킹입니다. 동기와 비동기는 작업 완료를 누가 신경 쓰느냐로, 결과를 직접 기다리거나 확인하면 동기이고 콜백에 맡기고 신경 쓰지 않으면 비동기라, 서로 다른 기준이므로 네 조합이 모두 가능합니다.

참고 자료:
- https://homoefficio.github.io/2017/02/19/Blocking-NonBlocking-Synchronous-Asynchronous/

## [COMMON-098] I/O Multiplexing이 무엇이고, 왜 필요한지 설명해 주세요.

답변:

I/O 멀티플렉싱은 한 스레드가 여러 소켓을 동시에 감시하다가 준비된 것만 골라 처리하는 방식입니다. 연결마다 스레드를 만들면 커넥션이 많을 때 메모리와 컨텍스트 스위칭 비용을 감당할 수 없는데, 이 방식은 적은 스레드로 많은 커넥션을 처리할 수 있습니다. select, poll, epoll 등이 있고 Nginx나 Redis 같은 서버가 이 구조로 동작합니다.

참고 자료:
- https://www.mimul.com/blog/io-multiplexing/

## [COMMON-099] WebSocket이 무엇이고, HTTP와 어떤 차이가 있는지 설명해 주세요.

답변:

WebSocket은 클라이언트와 서버가 연결을 유지하며 양방향으로 데이터를 주고받는 프로토콜입니다. HTTP 요청으로 연결을 시작해 서버가 승인하면 같은 연결이 WebSocket으로 전환됩니다. 요청과 응답의 단방향인 HTTP와 달리 서버가 먼저 데이터를 보낼 수 있어, 채팅이나 실시간 알림처럼 실시간 통신에 적합합니다.
