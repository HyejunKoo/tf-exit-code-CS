## [COMMON-081] OSI 7계층과 TCP/IP 4계층을 비교해 설명해 주세요.


답변:
OSI 7계층은 네트워크가 송수신 되는 과정을 1계층부터 7계층까지 단계별로 나눈 이론적인 모델이다. 
1계층은 physical 계층으로 데이터의 물리적 송수신을 담당하는 선 자체를 의미하고 
랜선, 광케이블이 1계층에 해당한다. 전기/광 신호로 비트 전송한다. 
2계층은 data link로 프레임화를 해서 MAC주소를 통해서 같은 LAN안에 존재하는 단말기들 중 MAC주소를 기반으로 어떤 단말기인지 확인하는 과정 
3계층은 Network 계층인데 이건 이제 라우터 간 데이터 이동을 의미해서 IP주소를 기반으로 "라우팅"한다 
4계층은 Transport 계층으로 IP주소로 그 디바이스 주소를 찾았다면 이제 그 디바이스와 데이터를 주고 받기 위한 준비를 하는 과정이다. 
in-order로 error없이 올바르게 도착하는걸 보장하는지 안하는지에 따라 TCP, UDP 프로토콜이 있다. 
그리고 포트번호를 통해 해당 디바이스의 어떤 application인지 확인 가능하다
5계층은 session 계층으로 통신 양끝단의 연결을 만들고 유지하고 끊는 관리 역할을 하며 
6계층은 Presentaion 계층으로 암호화되어있던 데이터를 상대방이 이해할 수 있는 형식으로 변환 및 번역하는 역할이다. 
7계층은 Application계층으로 이제 IP주소를 통해 어느 단말기인지 찾고 포트번호를 통해 application이 어떤건지 알고 통신 준비를 모두 마쳤으니 
보낼 메시지를 생성하는 곳이다. 


TCP/IP 4계층은 실무에서 실제로 사용하는 인터넷 표준 프로토콜 구조로 상위 3개 계층 (세션,표현,응용)을 응용 계층 하나로 두고 
물리, 데이터 링크는 네트워크 인터페이스 계층으로 하나로 합친 것이다. 
1계층은 네트워크 인터페이스 계층 : 같은 LAN 내부에서 MAC 주소를 사용해 전기, 광 신호 전달 
2계층 인터넷 계층 : IP 주소 기반 라우터 거쳐 네트워크 길 찾아가는 것 (라우팅) 
3계층 전송계층 : 포트번호를 이용해서 어떤 앱으로 갈지 구분 (신뢰성 기반으로 TCP, UDP 구분) 
4계층 응용 계층 : 사용자가 직접 사용하는 앱과 프로토콜이 동작하는 곳

## [COMMON-082] TCP와 UDP의 차이에 대해 설명해 주세요.

답변: 
TCP, UDP의 차이는 가장 크게 신뢰성을 보장하는지 안하는지에 대한 여부이다. 
TCP는 in-order로 error없이 올바르게 도창하는 걸 보장하는 프로토콜이라 헤더 길이가 길다. 
에러가 있다면 correction 기능도 포함해서 문제 생겼을때 다시 보내는 retrx도 진행한다.  
연결 상태에 대해서 3-way handshake로 미리 연결 맺고 신뢰성 있는 통신 지향하는 "연결 지향형"이다. 
또한 받는 사람이 처리할 수 있는 속도에 따라 flow control, congestion control 기능을 제공한다. 
UDP는 에러 있는지 확인은 하지만 correction까지는 진행해주지 않는 프토토콜로 TCP에 비해 제공하는 기능이 적어 
헤더가 짧고 받았는지 확인할 필요가 없어 우다다다 보내기때문에 속도가 빠르다.

## [COMMON-083] TCP 3-way handshake가 무엇이고, 왜 필요한지 설명해 주세요.

답변:
SYN - SYN/ACK - ACK 으로 이루어진 TCP가 서로 통신 전에 각 단말기끼리 확실하게 연결을 맺어두는 과정이다. 
SYN : 클라이언트가 서버에 연결 요청 (시퀀스 번호 x 전송) 
SYN-ACK : 서버가 승인(ACK X+1) 자신의 연결 받아달라는 SYN 보냄 (SYN Y) 
ACK : 서버의 SYN을 받겠다는 의미의 ACK (클라이언트 -> 서버 ACK Y+1) 

필요한 이유 : 양쪽 모두 데이터를 보낼 수 있고 받을 수 있는 지 양방향 통신가능 여부 확실하게 보증하기 위해서. 
데이터 손실이나 순서 역전 방지를 위해서 시퀀스 번호를 동기화하는 것도 중요함

## [COMMON-084] TCP 4-way handshake가 무엇이고, 연결 종료 과정에서 TIME_WAIT이 필요한 이유를 설명해 주세요.

답변:
3-way 핸드셰이크가 전화 걸어서 통화 시작하는 과정이었다면, 4-way 핸드셰이크는 서로 할 말 다 하고 안전하게 전화 끊는 과정이다. 

연결 종료 과정:
클라이언트 → FIN
서버 → ACK (자신의 처리 완료까지 대기)
서버 → FIN
클라이언트 → ACK 

FIN과 ACK이 분리되는 이유는 서버가 처리 중이던 데이터를 마저 전송할 시간이 필요하기 때문(TCP는 양방향 독립 종료 가능).

클라이언트가 마지막으로 ACK을 보내고 바로 연결을 끊지않고 일정시간 대기함 이러한 TIME_WAIT이 필요한 이유: 
마지막 ACK이 유실될 경우를 대비해 일정 시간 대기하며 재전송된 FIN에 재응답하기 위함
지연된 패킷(이전 연결의 패킷)이 새로운 연결로 잘못 전달되는 것을 방지하기 위함

## [COMMON-089] DNS가 무엇이고, 도메인 이름이 IP 주소로 변환되는 과정을 설명해 주세요.

답변:

naver.com 같은 도메인 주소를 컴퓨터가 이해하는 IP주소로 변환하는게 DNS가하는 일이다. 
* DNS는 일단 먼저 서버에 request 보내기 전에 IP주소 받은 후에 그걸 헤더에 담아서 http메시지를 만드는 것 

조회 과정:
브라우저/OS 캐시 확인
없으면 Local DNS Resolver(ISP 등)에 질의
Resolver가 Root DNS 서버에 질의 → TLD(.com 등) 서버 주소 반환
TLD 서버에 질의 → 해당 도메인의 권한 있는 네임서버(Authoritative NS) 주소 반환
Authoritative 서버에 질의 → 실제 IP 주소 반환
Resolver가 결과를 캐싱 후 클라이언트에 반환

## [COMMON-090] 브라우저에 URL을 입력했을 때 서버 응답을 받기까지의 흐름을 설명해 주세요.

답변:
1. URL 파싱 및 DNS 조회: 브라우저가 입력받은 URL을 분석하고, DNS를 통해 해당 도메인에 매핑된 서버의 IP 주소를 먼저 찾는다 

2. TCP 3-Way Handshake: 획득한 IP 주소와 포트 번호(HTTP 80, HTTPS 443)를 이용해 서버와 TCP 연결을 맺는다 

3. TLS/SSL Handshake:  Authentication 이후 데이터를 암호화할 대칭키(세션 키) 교환 

4. HTTP 요청 전송: 연결이 완료되면 브라우저가 서버로 HTTP Request 메시지를 생성해 전송

5. 서버 처리 및 응답 전송: 서버는 요청을 받아 로직을 처리하고 HTTP Response 메시지(HTML, JSON, 상태코드 200 OK)를 클라이언트에 반환

6. 브라우저 렌더링: 브라우저가 받은 응답 데이터(HTML, CSS, JS)를 파싱하여 화면에 화면을 그려준다 

7. TCP 4-Way Handshake: 통신이 끝나면 세션 종료 (HTTP Keep-Alive 설정 시 연결 유지)

## [COMMON-094] Cookie, Session, Token의 차이에 대해 설명해 주세요.

답변:
http는 기본적으로 stateless해서 서버에 클라이언트 정보를 저장해두지 않는다. 
그래서 사용자 인증 상태나 상태 정보를 유지하기 위해서 이러한 세션, 토큰, 쿠키를 사용한다. 

쿠키 : 클라이언트에 저장하는 것 / 서버가 응답 헤더(Set-Cookie)로 전달하면 브라우저에 저장되고, 이후 요청마다 자동으로 헤더에 포함되어 서버로 전송하는 것

쿠키는 서버 DB, 메모리 조회해서 사용자 정보를 알아야하지만 토큰은 stateless해서 토큰 문자열 안에 이미 사람, 이름, 권한, 유효기간이 암호화되어 들어있음

## [COMMON-095] Stateless하다는 것이 무엇이고, HTTP가 Stateless한 것이 어떤 장단점을 가지는지 설명해 주세요.

답변:
stateless하다는 건 서버가 클라이언트의 이전 요청, 상태 이력을 기억하지 않고 온전히 각 요청을 독립적으로 취급하는 것

## [COMMON-096] CORS가 무엇이고, 왜 발생하는지 설명해 주세요.

답변:
CORS는 한 출처(Origin)에서 실행 중인 웹 애플리케이션이 다른 출처의 리소스에 접근할 수 있도록 허용하는 브라우저의 보안 메커니즘이다. 
브라우저는 기본적으로 SOP라는 기능이 탑재되어있는데 기본적으로 다른 출처로의 http 요청이나 리소스 읽기를 차단해둠
출처(Origin)는 프로토콜 + 도메인 + 포트번호 조합을 뜻하며, 하나라도 다르면 다른 출처로 인식한다. 
예를 들어 리액트 클라이언트(localhost:3000)에서 백엔드 서버(localhost:8080)로 요청을 보낼 때 포트가 달라 SOP에 의해 차단되면서 CORS 에러가 발생함

## [COMMON-097] Blocking / Non-blocking과 Synchronous / Asynchronous의 차이에 대해 설명해 주세요.

답변:
- Blocking VS non blocking : 
	blocking은 호출된 함수가 자신의 작업 끝날때까지 제어권 쥐고 안넘겨줌 호출한 쪽은 작업이 끝날때까지 stop된 상태
	non blocking은 호출된 함수가 제어권 즉시 반환해서 호출한 쪽에서 대기 안하고 계속 다른 일 할 수 잇음 

- 동기 vs 비동기 
	동기 : 호출된 함수의 작업 완료 여부 신경 써서 순서 맞추는 것 
	비동기 : 호출된 함수에 콜백, 이벤트 전달을 통해서 작업 끝났을 때 처리되도록 하는 구조 
- 예시 
Sync-Blocking: 표준 Java I/O (읽기 작업 완료까지 멈춤)
Async-Non-blocking: Node.js I/O, JavaScript Promise/async-await (요청 후 안 기다리고 콜백으로 처리)

## [COMMON-098] I/O Multiplexing이 무엇이고, 왜 필요한지 설명해 주세요.

답변:

I/O Multiplexing: 하나의 스레드/프로세스가 여러 개의 I/O(소켓 등)를 동시에 감시하다가, 준비된 것(읽기/쓰기 가능해진 것)만 처리하는 기법. select, poll, epoll(Linux), kqueue(BSD/macOS) 등이 대표적.

왜 필요한가: 요청마다 스레드를 하나씩 만드는 방식(Thread-per-connection)은 커넥션이 많아질수록 컨텍스트 스위칭 비용과 메모리 사용량이 급증(C10K 문제). I/O Multiplexing을 쓰면 적은 수의 스레드로 수많은 연결을 효율적으로 처리 가능 → Nginx, Redis, Node.js 등 고성능 서버가 이 방식을 채택.

select vs epoll: select는 매번 전체 소켓 목록을 순회(O(n))하지만, epoll은 커널이 이벤트 발생한 소켓만 알려줌(O(1)에 가까움) → 대규모 연결에서 epoll이 훨씬 효율적.

## [COMMON-100] Load Balancing이 무엇이고, 어떤 방식들이 있는지 설명해 주세요.

답변:
서버 부하를 막아주기위해서 여러 서버로 트래픽을 분산시켜주는 기술을 의미한다. 
라운드 로빈 (Round Robin): 서버에 순서대로 요청을 균등하게 배분하는 방식 (가장 단순함)

가중 라운드 로빈 (Weighted Round Robin): 성능이 더 좋은 서버에 가중치를 부여하여 더 많은 요청을 배분

최소 연결 방식 (Least Connection): 현재 연결된 세션 수가 가장 적은 서버로 요청을 보냄 (작업 시간이 가변적일 때 유용)

IP 해시 방식 (IP Hash): 클라이언트의 IP 주소를 해싱하여 특정 서버로 매핑 (사용자가 항상 동일한 서버로 접속하도록 유도)
