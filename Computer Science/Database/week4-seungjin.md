## [COMMON-121] RDB와 NoSQL의 차이에 대해 설명해 주세요.

답변:

RDB는 데이터를 정해진 스키마의 테이블에 저장하고 테이블 간 관계를 엄격하게 정의하는 데이터베이스이고, NoSQL은 스키마가 유연해 key-value나 문서 형태로 저장하며 수평 확장에 유리합니다. RDB는 트랜잭션과 JOIN 덕분에 정합성이 중요한 곳에, NoSQL은 스키마가 자주 바뀌거나 트래픽이 많은 로그나 캐시에 적합해 실무에서는 둘을 함께 쓰기도 합니다.

## [COMMON-123] 정규화가 무엇이고, 정규화를 하지 않으면 어떤 이상 현상이 발생하는지 설명해 주세요.

답변:

정규화는 함수 종속을 기준으로 테이블을 분해해 데이터 중복과 이상 현상을 없애는 설계 과정입니다. 정규화가 안 되어 있으면 불필요한 값까지 함께 넣어야 하는 삽입 이상, 일부만 수정돼 데이터가 어긋나는 갱신 이상, 튜플을 지웠더니 필요한 정보까지 사라지는 삭제 이상이 생깁니다. 단계는 1NF, 2NF, 3NF, BCNF 순으로 종속을 점점 제거해 나갑니다.

## [COMMON-125] Join이 무엇이고, Inner Join과 Outer Join의 차이를 설명해 주세요.

답변:

JOIN은 두 개 이상의 테이블을 조인 조건으로 연결해 하나의 결과 집합으로 만드는 연산입니다. Inner Join은 조건을 만족하는 행만 가져와 교집합에 해당하고, Outer Join은 짝이 없는 행까지 포함해 기준 테이블의 행을 모두 남기고 빈 쪽은 NULL로 채웁니다. 기준을 어디에 두느냐에 따라 Left, Right, Full로 나뉩니다.

## [COMMON-126] 인덱스가 무엇이고, 왜 조회 성능을 향상시키는지 설명해 주세요.

## [COMMON-127] B-Tree와 B+Tree에 대해 설명하고, DB 인덱스에서 B+Tree가 많이 사용되는 이유를 설명해 주세요.

답변:

B-Tree는 한 노드가 여러 키와 자식을 갖고 모든 리프가 같은 레벨에 있는 균형 트리라 높이가 낮아 디스크 접근 횟수를 줄입니다. B+Tree는 데이터를 리프 노드에만 저장하고 내부 노드는 키만 가지며 리프끼리 연결 리스트로 이어진 구조입니다. DB 인덱스는 범위 조회가 많은데 B+Tree는 리프만 순서대로 따라가면 되고 높이도 더 낮출 수 있어 표준처럼 쓰입니다.

## [COMMON-130] 트랜잭션이 무엇이고, ACID에 대해 설명해 주세요.

답변:

트랜잭션은 여러 연산을 하나로 묶어 전부 반영되거나 전부 취소되게 만드는 논리적 작업 단위입니다. ACID는 이를 안전하게 보장하는 성질로, 부분 실행이 없는 원자성, 제약을 위반하지 않고 일관된 상태를 유지하는 일관성, 동시에 실행돼도 서로 간섭하지 않는 격리성, 커밋된 결과는 장애가 나도 남는 지속성입니다. 계좌 이체에서 출금만 되고 입금이 실패했을 때 롤백되는 것이 원자성의 예입니다.

## [COMMON-131] 트랜잭션 격리 수준에 대해 설명해 주세요.

답변:

격리 수준은 한 트랜잭션이 사용 중인 데이터를 다른 트랜잭션이 어디까지 볼 수 있게 할지 정하는 단계입니다. READ UNCOMMITTED, READ COMMITTED, REPEATABLE READ, SERIALIZABLE 순으로, 커밋 안 된 값까지 보이던 것에서 점점 제약이 강해져 마지막은 사실상 순차 실행처럼 동작합니다. 위로 갈수록 동시성이, 아래로 갈수록 정합성이 높아지는 트레이드오프이며 MySQL InnoDB 기본값은 REPEATABLE READ입니다.

## [COMMON-132] Dirty Read, Non-repeatable Read, Phantom Read에 대해 설명해 주세요.

답변:

셋 다 동시 트랜잭션 때문에 생기는 읽기 부정합이지만 원인이 다릅니다. Dirty Read는 커밋되지 않은 값을 읽어 상대가 롤백하면 존재하지 않는 데이터로 작업하게 되는 것이고, Non-repeatable Read는 같은 행을 다시 조회했을 때 다른 트랜잭션의 수정으로 값이 달라지는 것입니다. Phantom Read는 INSERT나 DELETE로 같은 조건의 결과 행 개수가 달라지는 것이라, 한 행이 아니라 집합에 초점이 있습니다.

## [COMMON-134] Optimistic Lock과 Pessimistic Lock의 차이에 대해 설명해 주세요.

답변:

비관적 락은 충돌이 날 것이라고 보고 조회 시점에 미리 DB 락을 걸어 다른 트랜잭션을 대기시키는 방식입니다. 낙관적 락은 락을 걸지 않고 진행하다가 version 같은 컬럼을 조건에 넣어 수정한 뒤 갱신된 행이 없으면 충돌로 판단해 애플리케이션에서 처리합니다. 그래서 충돌이 잦고 정합성이 중요하면 비관적 락이, 조회가 많고 충돌이 드물면 낙관적 락이 유리합니다.

## [COMMON-138] Cache Aside 패턴에 대해 설명해 주세요.

답변:

Cache Aside는 애플리케이션이 캐시를 먼저 확인하고 값이 있으면 반환, 없으면 DB에서 읽어 캐시에 채운 뒤 반환하는 전략으로 Look Aside라고도 합니다. 실제 조회된 데이터만 캐시에 올라가 메모리를 효율적으로 쓰고, 캐시가 죽어도 DB에서 읽으면 되어 장애가 전체로 번지지 않는 것이 장점입니다. 대신 첫 요청은 캐시 미스라 느리고, 쓰기가 캐시를 거치지 않아 DB만 바뀌면 캐시가 옛 값을 들고 있으므로 무효화 설계가 필요합니다.

## [COMMON-139] Redis와 같은 In-memory DB를 사용하는 이유를 설명해 주세요.

답변:

Redis 같은 인메모리 DB는 데이터를 디스크가 아니라 메모리에 두어 디스크 I/O 없이 조회하므로 응답이 훨씬 빠릅니다. 그래서 세션이나 토큰, 자주 조회되는 결과처럼 빠른 응답이 필요한 데이터를 올려 DB 부하를 줄이는 캐시 용도로 씁니다. List, Hash, Sorted Set 같은 자료구조로 랭킹이나 큐도 간단히 구현할 수 있지만, 메모리 용량 제한과 휘발성이 있어 스냅샷이나 AOF로 백업해야 합니다.

## [COMMON-140] SQL Injection이 무엇이고, 어떻게 방어할 수 있는지 설명해 주세요.

답변:

SQL Injection은 사용자 입력값이 쿼리 문자열에 그대로 붙어서, 데이터가 아니라 SQL 문법으로 해석되게 만드는 공격입니다. 조건을 항상 참으로 만드는 값을 넣어 인증을 우회하거나, 에러를 유발해 테이블과 컬럼 구조를 알아내는 식으로 악용됩니다. 근본적인 방어는 PreparedStatement로 쿼리를 먼저 컴파일하고 값을 바인딩해 입력이 문법이 아닌 데이터로만 처리되게 하는 것이고, 바인딩이 불가능한 자리는 화이트리스트로 검증합니다.

참고 자료:
- https://velog.io/@yanghl98/Database-SQL-Injection
