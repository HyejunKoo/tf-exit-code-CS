## [COMMON-121] RDB와 NoSQL의 차이에 대해 설명해 주세요.

답변: RDB는 정해진 스키마와 관계형 모델을 사용하고, NoSQL은 유연한 스키마로 대용량 분산 처리에 강하다. RDB는 정합성과 복잡한 조인이 강점이고, NoSQL은 확장성과 빠른 저장/조회에 유리하다. 예를 들면 MySQL, PostgreSQL 같은 RDB는 정형 데이터와 조인에 적합하고, MongoDB나 Cassandra 같은 NoSQL은 수평 확장과 빠른 처리에 적합하다.

## [COMMON-122] Primary Key, Candidate Key, Foreign Key, Unique Key의 차이에 대해 설명해 주세요.

답변: Primary Key는 행을 식별하는 대표 키이고, Candidate Key는 그 후보가 되는 키들이다. Unique Key는 중복을 허용하지 않지만 PK는 아니며, Foreign Key는 다른 테이블의 PK를 참조한다. Primary Key는 보통 NOT NULL과 UNIQUE 제약을 함께 가진다.

## [COMMON-123] 정규화가 무엇이고, 정규화를 하지 않으면 어떤 이상 현상이 발생하는지 설명해 주세요.

답변: 정규화는 중복을 줄이고 데이터 일관성을 높이기 위해 테이블을 구조화하는 과정이다. 하지 않으면 삽입, 갱신, 삭제 이상이 생길 수 있다. 예를 들어 하나의 테이블에 고객 정보와 주문 정보가 섞여 있으면 고객 정보를 한 번만 바꿔도 여러 행을 수정해야 한다.

## [COMMON-125] Join이 무엇이고, Inner Join과 Outer Join의 차이를 설명해 주세요.

답변: Join은 여러 테이블의 관련 데이터를 조건에 맞게 결합하는 연산이다. Inner Join은 조건이 맞는 행만, Outer Join은 한쪽에 없어도 나머지 행을 포함한다. Left, Right, Full Outer Join으로 누락되는 쪽을 기준에 맞게 보완할 수 있다.

답변: 인덱스는 데이터를 빠르게 찾기 위한 보조 구조다. 전체를 훑지 않고 원하는 위치를 빠르게 찾아가므로 조회 성능이 좋아진다. B+Tree 기반 인덱스는 범위 검색과 정렬에도 유리하다.

## [COMMON-127] B-Tree와 B+Tree에 대해 설명하고, DB 인덱스에서 B+Tree가 많이 사용되는 이유를 설명해 주세요.

답변: B-Tree는 내부 노드와 리프 노드 모두에 데이터를 둘 수 있고, B+Tree는 실제 데이터를 리프에만 둔다. B+Tree는 리프 연결로 범위 조회에 강하고 탐색 성능이 안정적이라 인덱스에 많이 쓰인다. 리프 노드가 연결 리스트처럼 이어져 있어서 정렬된 순회가 빠르다.

## [COMMON-130] 트랜잭션이 무엇이고, ACID에 대해 설명해 주세요.

답변: 트랜잭션은 여러 작업을 하나의 논리 단위로 묶어 처리하는 것이다. ACID는 Atomicity(원자성), Consistency(일관성), Isolation(고립성), Durability(지속성)의 약자로, 트랜잭션의 신뢰성을 보장한다. 원자성은 전부 성공하거나 전부 실패하는 것이고, 지속성은 커밋된 결과가 장애 후에도 남는다는 뜻이다.

## [COMMON-131] 트랜잭션 격리 수준에 대해 설명해 주세요.

답변: 격리 수준은 동시에 실행되는 트랜잭션 간에 서로 얼마나 보이지 않게 할지 정하는 기준이다. 낮을수록 성능은 좋지만 이상 현상이 늘고, 높을수록 정합성은 좋지만 동시성이 줄어든다. 대표적으로 Read Uncommitted, Read Committed, Repeatable Read, Serializable이 있다.

## [COMMON-132] Dirty Read, Non-repeatable Read, Phantom Read에 대해 설명해 주세요.

답변: Dirty Read는 커밋되지 않은 데이터를 읽는 경우, Non-repeatable Read는 같은 행을 두 번 읽었을 때 값이 바뀌는 경우다. Phantom Read는 같은 조건으로 다시 조회했을 때 행 수 자체가 달라지는 현상이다. 보통 격리 수준이 높아질수록 이런 현상을 더 잘 막는다.

## [COMMON-133] DB Lock이 무엇이고, Shared Lock과 Exclusive Lock의 차이에 대해 설명해 주세요.

답변: Lock은 동시에 수정될 때 생기는 충돌을 막기 위한 제어 장치다. Shared Lock은 여러 읽기를 허용하고 쓰기는 막으며, Exclusive Lock은 읽기와 쓰기 모두를 막는다. 실무에서는 행 수준 Lock을 자주 쓰지만, 상황에 따라 테이블 수준 Lock도 발생할 수 있다.

## [COMMON-134] Optimistic Lock과 Pessimistic Lock의 차이에 대해 설명해 주세요.

답변: Optimistic Lock은 충돌이 드물다고 보고 수정 시점에 버전 비교로 검증한다. Pessimistic Lock은 충돌 가능성을 높게 보고 미리 잠가서 충돌을 막는다. 전자는 버전 컬럼이나 수정 시간을 비교하고, 후자는 SELECT ... FOR UPDATE처럼 선점하는 방식이 많다.

## [COMMON-141] 기본키는 인덱스라고 할 수 있을까요? 기본키와 인덱스의 관계를 설명해 주세요.

## [COMMON-142] 외래키는 자동으로 인덱스가 생성될까요? DBMS별로 차이가 있을 수 있는 이유를 설명해 주세요.

답변: DBMS마다 다르다. 예를 들어 MySQL InnoDB는 외래키 컬럼에 인덱스가 없으면 자동으로 만들거나 요구하는 편이고, PostgreSQL은 외래키 인덱스를 자동으로 만들지 않아 사용자가 직접 생성해야 한다. 이런 차이는 각 DBMS의 제약 조건 검사 방식과 옵티마이저 전략이 다르기 때문이다. SQL Server나 Oracle도 제약 처리 방식과 인덱스 생성 정책이 서로 다를 수 있다.

## [COMMON-148] WAL, Redo Log, Undo Log의 역할을 설명해 주세요.

답변: WAL은 변경 내용을 먼저 로그에 남겨 장애 복구를 가능하게 하는 방식이다. Redo Log는 커밋된 변경을 재적용하고, Undo Log는 롤백이나 MVCC를 위해 이전 값을 보관한다. WAL 덕분에 데이터 파일에 바로 쓰지 않아도 복구가 가능하다.

## [COMMON-149] MySQL InnoDB의 MVCC가 무엇인지 설명해 주세요.

답변: MVCC는 버전 정보를 이용해 읽기와 쓰기를 분리하는 기법이다. InnoDB는 undo log와 트랜잭션 정보를 활용해 일관된 스냅샷 읽기를 제공한다. 같은 행의 이전 버전을 유지해 읽기 작업이 쓰기와 덜 충돌하게 만든다.

## [COMMON-150] DB Replication이 무엇이고, Master-Slave 구조의 장단점을 설명해 주세요.

답변: Replication은 데이터를 여러 DB에 복제해 가용성과 읽기 성능을 높이는 방식이다. Master-Slave 구조는 읽기 분산이 쉽지만, 쓰기는 마스터에 집중되고 복제 지연이 생길 수 있다. 장애 시 슬레이브 승격 같은 failover 전략도 함께 고려한다.

## [COMMON-153] Partitioning과 Sharding의 차이를 설명해 주세요.

답변: Partitioning은 보통 하나의 DB 내부에서 논리적으로 나누는 것이고, Sharding은 여러 DB 서버로 물리적으로 분산하는 것이다. Partitioning은 관리가 단순하고, Sharding은 확장성이 더 크다. 즉, partition은 주로 엔진 내부 최적화, shard는 시스템 아키텍처 확장에 가깝다.

## [COMMON-154] NoSQL에서 Eventual Consistency가 무엇인지 설명해 주세요.

## [COMMON-155] CAP 이론에 대해 설명해 주세요.

답변: CAP 이론은 분산 시스템에서 Consistency, Availability, Partition Tolerance를 동시에 완벽히 만족할 수 없다는 개념이다. 실제 시스템은 네트워크 분할을 전제로 C와 A 사이에서 우선순위를 정한다. RDB는 보통 C를, 일부 NoSQL은 A와 P를 더 강하게 가져가는 식으로 설계한다.

## [COMMON-157] Write-through, Write-back, Write-around 캐시 전략을 설명해 주세요.

답변: Write-through는 쓰기 시 캐시와 DB를 동시에 갱신하고, Write-back은 캐시에 먼저 쓰고 나중에 DB에 반영한다. Write-around는 캐시를 거치지 않고 DB에만 쓰며, 읽힐 때 캐시에 적재한다. 쓰기 빈도와 데이터 중요도에 따라 전략을 고른다.
