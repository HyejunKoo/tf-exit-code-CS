## [COMMON-122] Primary Key, Candidate Key, Foreign Key, Unique Key의 차이에 대해 설명해 주세요.

답변: 
- Candidate Key: 각 행을 유일하게 식별할 수 있는 최소 컬럼 집합이다.
- Primary Key: Candidate Key 중 대표로 선택한 키다. 중복과 NULL을 허용하지 않는다.
- Foreign Key: 다른 테이블의 Primary Key나 Unique Key를 참조하여 테이블 간 관계를 만든다. 
- Unique Key: 컬럼 값의 중복을 제한하는 키. Primary Key와 달리 테이블에 여러 개 만들 수 있으며, NULL 허용 여부는 DBMS에 따라 다르다.

## [COMMON-125] Join이 무엇이고, Inner Join과 Outer Join의 차이를 설명해 주세요.

답변: JOIN은 관련 컬럼을 기준으로 여러 테이블의 데이터를 결합하여 조회하는 연산. 
- Inner join: 양쪽 테이블에서 조인 조건을 만족하는 행만 반환
- Left Outer Join: 왼쪽 테이블의 모든 행 반환, 오른쪽에 대응되는 데이터가 없으면 NULL반환
- Right Outer Join: 오른쪽 테이블의 모든 행 반환
- Full Outer Join: 양쪽 테이블의 모든 행 반환

## [COMMON-127] B-Tree와 B+Tree에 대해 설명하고, DB 인덱스에서 B+Tree가 많이 사용되는 이유를 설명해 주세요.

## [COMMON-130] 트랜잭션이 무엇이고, ACID에 대해 설명해 주세요.

답변: 트랜잭션으 하나의 논리적인 작업 단위로 처리되는 연산의 집합. 모든 작업이 성공하면 commit, 하나라도 실패하면 rollback

atomicity: 작업이 모두 수행되거나 모두 취소되어야 한다.
consistency: 트랜잭션 전후에 데이터이ㅡ 제약조건과 일관성이 유지돼야 한다.
isolation: 동시에 실행되는 트랜젝션이 서로의 중간상태에 영향을 주지 않아야 한다.
durability: commit된 데이터는 장애가 발생해도 보존돼야 한다.

## [COMMON-131] 트랜잭션 격리 수준에 대해 설명해 주세요.

답변: 트랜잭션 격리수준은 동시에 실행되는 트랜잭션이 서로의 변경 내용을 어느 범위까지 볼 수 있는지 정의
- read uncommitted: commit되지 않은 데이터도 읽을 수 있다.
- read committed: commit된 데이터만 읽을 수 있다.
- repeatable read: 같은 트랜잭션에서 동일 행을 반복 조회할 때 같은 결과 보장
- serializable: 트랜잭션을 순차적으로 실행한 것과 같은 결과를 보장
격리수준이 높을수록 일관성은 강화되지만 잠금 대기, 충돌로 인해 동시 처리 성능이 낮아질 수 있다.

## [COMMON-132] Dirty Read, Non-repeatable Read, Phantom Read에 대해 설명해 주세요.

답변: 
dirty read: 다른 트랜잭션이 아직 commit하지 않은 데이터를 읽는 현상
non-repeatable read: 같은 행을 다시 조회했을 때 다른 트랜잭션의 수정이나 삭제로 값이 달라지는 현상

## [COMMON-133] DB Lock이 무엇이고, Shared Lock과 Exclusive Lock의 차이에 대해 설명해 주세요.

답변: DB Lock은 여러 트랜잭션이 같은 데이터에 동시 접근할 때 데이터 일관성을 보호하기 위한 동시성 제어 방식
- shared lock: 데이터를 읽기 위한 잠금. 여러 트랜잭션이 동시 획득 가능
- exclusive lock: 데이터 수정, 삭제하기 위한 잠금. 다른 shared lock과 exclusive lock의 획득 제한
잠금을 오래 유지하면 대기시간, deadlock가능성 증가 -> 트랜잭션 범위를 짧게 유지해야 한다.

## [COMMON-134] Optimistic Lock과 Pessimistic Lock의 차이에 대해 설명해 주세요.

답변: optimistic lock은 충돌이 적다고 가정하고 실제 db잠금을 먼저 획득하지 않는다. 수정 시 버전 번호, 수정시간을 비교하여 ㅏㄷ른 작업이 데이터를 변경했는지 확인. 충돌하면 실패처리 or 재시도. pessimistic lock: 충돌이 많다고 가정하고 데이터를 사용하기 전에 SELECT FOR UPDATE등의 방식으로 잠금 획득
Optimistic lock은 동시성이 높지만 재시도 처리 필요, pessimistic lock은 충돌 예방 but 대기시간, deadlock가능성이 커진다.

## [COMMON-135] DB Deadlock이 발생하는 상황과 해결 방법에 대해 설명해 주세요.

답변: deadlock은 여러 트랜잭션이 서로 보유한 잠금이 해제되기를 순환 형태로 기다리는 상황. 예를 들어 트랜잭션 a가 데이터 1을 잠근 후 데이터 2를 기다리고, 트랜잭션 b가 데이터 2를 잠근 후 데이터 1을 기다리면 deadlock발생. 
해결 및 예방방법
- 데이터 접근 순서 통일
- 트랜잭션 범위, 실행시간 줄이기
- 적절한 인덱스로 잠금 범위 줄이기
- 한 번에 수정하는 데이터 수 줄이기
- deadlock으로 rollback된 트랜잭션에 재시도 로직 허용

## [COMMON-137] Cache를 사용하는 이유와 주의해야 할 점을 설명해 주세요.

답변: cache는 자주 조회하거나 계산비용이 높은 데이터를 빠른 저장소에 보관하여 응답시간을 줄이고 DB부하를 낮추기 위해 사용한다. 주의할 점은 다음과 같다.
- 원본 데이터와 캐시 데이터 간의 불일치
- 캐시 만료 시 요청이 한꺼번에 DB로 몰리는 Cache Stampede
- 존재하지 않는 데이터를 반복 조회하는 Cache Penetration
- 특정 키에 요청이 집중되는 Hot Key
- 메모리 부족과 잘못된 Eviction 정책
- 캐시장애가 전체 서비스 장애로 이어지는 문제
TTL, 캐시 무효화 정책, 만료 시간 분산과 함꼐 장애 대응 방안을 함께 설계해야 한다.

## [COMMON-139] Redis와 같은 In-memory DB를 사용하는 이유를 설명해 주세요.

## [COMMON-140] SQL Injection이 무엇이고, 어떻게 방어할 수 있는지 설명해 주세요.
