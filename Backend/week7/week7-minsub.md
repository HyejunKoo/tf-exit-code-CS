## [ROLE-041] Java에서 객체 생성과 메모리 할당이 어떻게 이루어지는지 Heap과 Stack 관점에서 설명해 주세요.

답변: Java에서 객체는 `new` 카워드를 통해 생성되고 지역 변수는 스택 프레임에, 객체는 힙에 저장됩니다.

`User user = new User()`라고 하면 `User` 객체는 힙에 생성되고, 지역 변수 `user`는 스택 프레임에 저장되면서 힙 객체를 참조하게 되는 것.

스택은 메서드 호출마다 생성되는 스택 프레임을 저장하는 공간으로, 지역 변수, 매개 변수, 메서드 호출 정보 등이 저장되고, 메서드가 종료되면 해당 스택 프레임은 제거됩니다.

반면에 힙은 객체가 저장되는 공간이고, 메서드가 종료돼도 객체를 참조하는 곳이 남아 있으면 계속 살아 있을 수 있습니다. 

여기서 객체를 더 이상 참조하는 곳이 없으면 GC의 대상이 됩니다. 그래서 자바에선 객체 생명주기를 직접 `free` 시키지 않고, jvm의 gc가 관리합니다.

## [ROLE-042] JVM Garbage Collector의 Young Generation과 Old Generation 개념을 설명해 주세요.

답변: JVM의 힙은 일반적으로 Young Generation과 Old Generation으로 나뉩니다.
대부분의 객체가 생성된 직후 짧은 시간 안에 더 이상 사용되지 않는다는 가정에 기반합니다.

Young Generation은 새로 생성된 객체가 먼저 할당되는 영역으로 Eden 영역과 Survivor 영역이 있고, 객체는 처음 Eden에 생성됩니다.
마이너 GC가 발생하면 살아남은 객체는 Survivor 영역으로 이동하고, 여러 번 살아남은 객체는 Old Generation으로 승격될 수 있습니다.

Old Generation은 비교적 오래 살아남은 객체들이 저장되는 영역입니다. Old Generation이 가득 차면 Major GC나 Full GC가 발생할 수 있고, 이 과정은 Young Generation GC보다 비용이 클 수 있습니다.

백엔드 서버에서는 요청마다 많은 임시 객체가 생성되기 때문에 Young Generation GC가 자주 발생할 수 있습니다.
객체 생성량이 과도하거나 오래 참조되는 객체가 많으면 Old Generation 사용량이 증가하고, 결국 긴 GC Pause나 OOM으로도 이어질 수 있다고 알고 있습니다.

## [ROLE-043] Minor GC와 Major GC 또는 Full GC의 차이를 설명해 주세요.

답변: Minor GC는 Young Generation을 대상으로 수행되는 GC입니다. 새로 생성된 객체 중 더 이상 참조되지 않는 객체를 정리하고, 살아남은 객체는 Survivor 영역으로 이동하거나 일정 조건을 만족하면 Old Generation으로 승격됩니다.

Major GC는 일반적으로 Old Generation을 대상으로 하는 GC를 의미합니다. Old Generation에는 오래 살아남은 객체들이 있기 때문에 Young Generation보다 정리 비용이 큰 경우가 많습니다.

Full GC는 힙 전체뿐 아니라 경우에 따라 Method Area 또는 Metaspace까지 포함해 더 넓은 범위를 정리하는 GC를 말합니다.
Full GC는 Stop-The-World 시간이 길어질 수 있어, 서버 응답 지연에 큰 영향을 줄 수도 있습니다.

실무에선 GC 종류의 용어가 GC 알고리즘이나 JVM 구현에 따라 조금 다르게 사용될 수도 있어서, 단순 이름만 보기보다 GC 로그에서 어떤 영역이 수집되었는지, Pause 시간이 얼마나 발생했는지, Old 영역이 계속 증가하는지 확인하는 것이 중요하다고 봅니다.

- STOP-THE-WORLD: GC 등의 작업을 위해 JVM이 애플리케이션 스레드의 실행을 일시적으로 중단하는 구간.

## [ROLE-044] Java에서 OutOfMemoryError가 발생할 수 있는 원인과 대응 방법을 설명해 주세요.

답변: 자바에서 OOM 에러는 JVM이 메모리를 더 이상 확보하지 못할 때 발생합니다. 대표적으로 힙 메모리, 메타스페이스 등이 부족한 경우나 스레드가 너무 많이 생성돼서 Native Memory가 부족한 경우 등이 있는데요

힙 OOM은 객체가 계속 생성되는 상황에서 GC로 회수되지 않을 때 발생할 수 있습니다.
뭐 static 컬렉션에 데이터를 계속 쌓거나, 캐시에 TTL이나 용량 제한을 두지 않거나, 대용량 데이터를 한 번에 메모리에 올리는 경우가 있습니다.

대응할 땐 먼저 힙 덤프와 GC 로그를 확인해서 어떤 객체가 메모리를 많이 차지하는지 분석해야 합니다. 이후에 불필요한 참조를 제거하고, 캐시 크기랑 TTL을 설정하고, 대용량 조회의 경우에는 페이징이나 스트리밍 방식으로 바꿀 수 있겠습니다.
단순히 JVM 힙 크기만 늘리는 것은 또 임시 대응일 수 있고, 근본 원이 메모리 누수면 다시 문제가 발생할 수 있습니다.

그래서 OOM은 메모리 부족 현상이긴 하지만, 원인은 객체 생성 패턴, 참조 유지, 캐시 정책, 스레드 수, JVM 설정 등 다양한 원인으로 발생할 수 있어서 로그와 덤프 기반으로 파악해야 되는 문제입니다.

답변: 자바에서 동시성 문제는 여러 스레드가 같은 공유 자원을 동시에 읽고, 수정할 때 발생합니다. 해결 방법으론 `Atomic` 클래스, `synchronized`, `Lock` 등을 사용할 수 있습니다.

## [ROLE-046] ConcurrentHashMap이 HashMap과 어떤 차이를 가지며, 멀티스레드 환경에서 왜 필요한지 설명해 주세요.

답변: 해시맵은 기본적으로 Thread-safe하지 않습니다. 여러 스레드가 동시에 해시맵에 데이터를 추가하거나 수정하면 데이터 유실, 무한 루프, 구조 손상 같은 문제가 발생할 수 있습니다.

ConcurrentHashMap은 멀티스레드 환경에서 안전하게 사용할 수 있도록 설계된 Map 구현체입니다.
전체 맵에 하나의 큰 락을 거는 방식이 아니라, 내부적으로 동시 접근을 더 세밀하게 제어해 여러 스레드가 동시에 읽고 일부 쓰기 작업을 수행할 수 있게 합니다.

또 ConcurrentHashMap은 null key와 null value를 허용하지 않습니다. 멀티스레드 환경에서 널을 허용하면 `get()`결과가 값이 없는 것인지, null인 것인지 구분하기 아려워질 수 있습니다.

- HashMap: 단일 스레드나, 외부 동기화가 보장된 경우
- ConcurrentHashMap: 여러 스레드나 동시에 접근하는 공유 맵이 필요한 경우 사용

## [ROLE-048] Spring에서 Circular Dependency가 무엇이고, 왜 문제가 되는지 설명해 주세요.

답변: Circular Dependency는 두 개 이상의 빈이 서로 의존하는 상황입니다.
A 서비스가 B 서비스를 필요로 하고, B 서비스도 다시 A 서비스를 필요로 하는 구조가 대표적입니다.

특히 생성자 주입에서 A를 만들기 위해 B가 필요하고, B를 만들기 위해 다시 A가 필요한 상황이 돼서 빈 생성이 실패할 수 있습니다.

세터 주입이나 필드 주입에선 일부 순환 참조가 동작할 수 있지만, 이는 근본 해결이라기보다 설계 문제를 숨기는 경우가 많습니다.

해결법은 두 빈의 책임을 재검토하고, 공통 책임을 별도 서비스로 분리하거나, 이벤트 발행 구조를 바꾸거나, 의존 방향을 단방향으로 정리하는 방법 등이 있겠습니다.

## [ROLE-049] Spring AOP의 Proxy 기반 동작 방식과 Self Invocation 문제가 무엇인지 설명해 주세요.

답변: 스프링 AOP는 기본적으로 프록시 기반으로 동작합니다. 스프링이 대상 빈을 감싼 프록시 객체를 만들고, 외부에서 빈 메서드를 호출할 때 실제 객체가 아니라 프록시를 통해 호출되도록 합니다. 

Self Invocation 문제는 같은 클래스 내에서 자기 자신의 메서드를 호출할 때 발생합니다. 같은 클래스 안의 `this.innerMethod()`를 호출하면 스프링 프록시를 거치지 않고, 실제 객체 내부 메서드를 직접 호출합니다.

이런 경우에 `innerMethod()`에 `@Transactional`이나 AOP 어노테이션이 붙어 있어도 프록시를 통과하지 않기 때문에 AOP가 적용되지 않을 수 있습니다.

## [ROLE-050] @Transactional이 적용되지 않는 대표적인 상황과 그 이유를 설명해 주세요.

답변: 같은 클래스 내부에서 자기 자신의 메서드를 호출하는 경우입니다.

스프링의 선언적 트랜잭션은 프록시 기반으로 동작해서 외부에서 프록시를 통해 호출돼야 트랜잭션 부가 기능이 적용됩니다.

## [ROLE-054] JPA Dirty Checking이 무엇이고, 어떤 조건에서 동작하는지 설명해 주세요.

답변: Dirty Checking은 영속 상태의 엔티티 변경 사항을 JPA가 감지해 자동으로 update SQL을 생성하는 기능입니다. 

JPA는 엔티티가 영속성 컨텍스트에 들어올 때 최소 상태를 스냅샷으로 저장합니다. 이후 트랜잭션 커밋이나 flush 시점에 현재 엔티티 상태와 스냅샷을 비교하고, 변경된 값이 있으면 update SQL을 생성합니다.

Dirty checking이 동작하려면 엔티티가 영속 상태여야 되고, 트랜잭션 범위 안에서 변경이 이루어져야 합니다.
반대로 준영속이면 엔티티를 수정하거나, 트랜잭션 밖에서 변경하면 Dirty Checking이 기대한 대로 동작하지 않을 수 있습니다.

따라서 JPA에선 단순히 세터를 호출했다고 DB에 반영되는 게 아니라, 해당 엔티티가 영속성 컨텍스트에 의해 관리되고 있는지가 중요합니다.

## [ROLE-055] JPA에서 연관관계의 주인이 무엇이고, 왜 필요한지 설명해 주세요.

답변: JPA에서 연관관계의 주인은 외래키를 관리하는 쪽입니다. 양방향 연관관계에선 두 객체가 서로를 참조하지만, 실제 DB에는 외래키가 한쪽 테이블에만 존재합니다. 그래서 JPA는 둘 중 어느 쪽 변경을 기준으로 업데이트를 할지 정해야 합니다.

예를 들어 `Member`와 `Team`이 다대일 관계인데, DB 외래키는 보통 `member.team_id`에 있으니까, 이 경우 `Member`가 연관관계 주인이 되고, `Team.members`는 `mappedBy`로 읽기용 반대편 관계가 됩니다.

## [ROLE-056] JPA에서 Cascade와 Orphan Removal의 차이를 설명해 주세요.

답변: Cascade는 부모 엔티티의 영속성 작업을 자식 엔티티에도 전파하는 것입니다. (부모 저장 -> 자식 저장 / 부모 삭제 -> 자식 삭제)

Orphan Removal는 부모와의 연관관계가 끊어진 자식 엔티티를 고아 객체로 보고 삭제하는 기능입니다.
예를 들어서 `order.getItems().remove(item)`처럼 컬렉션에서 자식이 제거되면, 해당 자식 엔티티를 DB에서도 삭제할 수 있습니다. 

두 옵션 모두 삭제와 관련된 영향을 줘서, 자식 엔티티의 생명 주기가 부모에 완전히 종속될 때 사용하는 것이 좋습니다.

## [ROLE-057] Spring Security에서 SecurityFilterChain이 어떤 역할을 하는지 설명해 주세요.

답변: Spring Security는 Servlet Filter 기반으로 동작하고, `SecurityFilterChain`은 어떤 요청에 어떤 보안 필터들을 적용할지 정의하는 구간입니다.

클라이언트 요청이 들어오면 Spring Security의 `FilterChainProxy`가 요청에 맞는 `SecurityFilterChain`을 선택하고, 그 안에 등록된 여러 보안 필터를 순서대로 실행합니다.

이 필터들은 인증 정보 추출, 세션 관리, CSRF, 로그아웃 처리, 인가 검사 등을 담당합니다.

예를 들어 JWT 기반 인증에선 SecurityFilterChain에 JWT 검증 필터를 추가할 수 있습니다. 이 필터는 요청의 Authorization 헤더에서 토큰을 꺼내 검증하고, 인증된 사용자 정보를 SecurityContext에 저장합니다.

## [ROLE-058] 인증(Authentication)과 인가(Authorization)의 차이를 Spring Security 관점에서 설명해 주세요.

답변: 인증은 사용자가 누구인지 확인하는 과정입니다. 로그인 요청에서 아이디, 비밀번호를 검증하고, JWT 토큰을 검증해 사용자를 식별하는 게 인증입니다.

인가는 인증된 사용자가 특정 리소스나 기능에 접근할 권한이 있는지 확인하는 과정입니다.
그래서 예를 들어 일반 사용자가 관리자 API에 접근할 수 없도록 막는 것이 인가입니다.

Spring Security에선 인증이 성공하면 Authentication 객체가 SecurityContext에 저장됩니다. 이후 인가 단계에서 이 Authentication 안에 들어 있는 사용자 정보와 권한을 기반으로 요청 접근 가능 여부를 판단합니다.

## [ROLE-059] Refresh Token을 사용할 때 Access Token 탈취, Refresh Token 탈취에 각각 어떻게 대응할 수 있는지 설명해 주세요.

답변: 액세스 토큰은 실제 API 요청에 사용되는 토큰이고, 탈취되면 만료 전까지 공격자가 API 호출이 가능해서 보통 시간을 짧게 설정합니다.

액세스 토큰 블랙리스트, 토큰 버전 관리, 사용자 상태 검증으로 강제 무효화를 구현할 수 있기는 하지만, 서버 저장소 조회가 필요하니까 JWT의 stateless 장점이 줄어듭니다.

그래서 리프레시 토큰은 액세스 토큰을 재발급하기 위한 토큰이고, 보통 액세스 토큰보다 길게 설정합니다.
다만, 리프레시 토큰이 탈취되면 피해가 더 커질 수 있습니다. 그래서 리프레시 토큰의 경우 Redis에 저장하고 로그아웃 시에 폐기하며, 재발급 시마다 기존 리프레시 토큰을 폐기하고 새 토큰을 발급하는 교체 전략을 사용합니다.

리프레시 토큰 재사용 감지로 폐기된 리프레시 토큰이 다시 사용되면 탈취로 판단하고, 해당 사용자의 모든 토큰을 무효화 할 수 있습니다.

- 액세스 토큰 -> 짧은 만료 시간으로 피해 범위 줄임
- 리프레시 토큰 -> 서버측 저장과 교체, 재사용 감지 관리

## [ROLE-060] Spring 백엔드에서 동시 요청으로 인한 재고 차감 Race Condition을 어떻게 해결할 수 있는지 설명해 주세요.

답변: 재고 차감 Race Condition은 여러 요청이 동시에 같은 재고 데이터를 읽고 수정할 때 발생합니다. 예를 들어 재고가 1개 남았는데 두 사용자가 동시에 주문하면, 두 요청이 모두 재고가 있다고 판단해 주문이 2건 생성될 수 있습니다.

그래서 이런 상황엔 재고 조회와 차감을 원자적으로 처리해 해결합니다. 기본적으로 DB 트랜잭션을 적용하고, 필요한 경우 Lock을 적용해야 합니다.

비관적 락은 `SELECT ... FOR UPDATE`처럼 해당 row를 먼저 잠궈서 작업하는 방식입니다.
충돌이 많으면 정합성을 강하게 보장하기 좋지만, 대기 시간이 길어지고 데드락 가능성이 있습니다.

낙관적 락은 version 컬럼을 두고 수정 시점에 version이 바뀌었는지 확인하는 방법입니다. 충돌이 적을 때 성능상 좋지만, 충돌 발생 시에 재시도나 실패 처리가 필요하죠.

보통 단순 재고 차감은 SQL에서 `UPDATE product SET stock = stock - 1 WHERE id = ? AND stock > 0`처럼 조건부 update로 처리하고, update row 수를 확인하는 방식도 사용할 수 있습니다.
다만, 분산 서버 환경에선 애플리케이션 내부 synchronized만으론 여러 인스턴스 간 동시성을 막을 수 없으므로 DB Lock, Redis 분산 락, 메시지 큐 기반 순차 처리 등을 고려해야 합니다.
